# 长程运行的上下文设计

2026-10-19 起草。这份文档讲的是「常驻 Bot 长期用下去，上下文怎么办」的整体设计：要达成什么、大致是什么样、每条规则为什么是这样。被推翻的决定记 [ADR](../adr/)。

这是**开发态的设计**，还没完全落地，所以放在 `docs/dev/`：写的是打算怎么做，不是仓库现在的样子。落地完之后删掉本文，把现行行为提炼进 [atlas/context.md](../atlas/context.md)——那边才是仓库现状的唯一说法。

## 30 秒版

发给模型的上下文不是聊天记录，而是每轮现拼的一份工作记忆。它有两条线，都从模型推出来：到**软目标**就在后台慢慢整理，不挡这一轮；只有逼近**硬上限**才当场压。聊天记录在磁盘上始终完整，几百轮都在。工作记忆分三段：不变的开头、摘要块、最近几轮的原文。

里面装的东西分三种，处理方式各不相同。**历史**只增不减，靠压缩把最旧的一段搬成摘要块，付一次钱，之后按摘要的大小付费。**状态**每轮只有一个当前值（几点、有哪些工具、记忆长什么样），旧的立刻作废，靠「变了才发、发在尾部、发的时候说明它取代之前那份」处理，不搬也不删。**提醒**是「此刻该知道的一件事」（文件变了、后台跑完了、卡还挂着），由事件触发，独立成一条进上下文，但不占聊天记录的行。搬走不等于丢掉：原文一直在磁盘上，能按序号读回、能全文搜索。

## 要做成什么样

一个 Bot 连续用几个月，不换会话：

- 第 200 轮和第 20 轮的响应速度、成本、准确度在一个量级。
- 上下文占用稳定在软目标附近，不随轮数增长，也从不碰硬上限。
- 正常对话里不会因为压缩停下来等；只有一下子涌进很多内容、逼近硬上限时才会。
- 回头问第 1 轮说过的事实，答得出来。
- 压缩本身花掉的 token，不超过这段时间总消耗的 2%。

## 为什么必须有上限

模型没有记忆。每一轮都要把全部上下文重新发一遍，第 200 轮时前 199 轮也要再付一次，累计成本随轮数平方增长。不设上限，一个长期 Bot 会越用越贵。

现在模型窗口普遍到 1M 了。装得下不等于该装：越满越慢、越贵，长上下文里模型自己的注意力也会分散。所以窗口只当天花板，不当目标。

## 两条线：软目标和硬上限

「该整理了」和「必须当场压」是两件事，用两条线表达（[ADR 0015](../adr/0015-soft-target-hard-ceiling.md)）：

```text
0 ────────── 软目标 T ──────────────── 硬上限 H ── 窗口
   正常对话   │  后台在两轮之间整理，不挡这一轮 │ 只有到这里才轮内同步压
```

- **硬上限 H＝窗口 − 输出预留 − 工具定义 − 估算余量（约 10%）。** 过了它请求会被拒，所以只有它能让这一轮停下来等压缩。
- **软目标 T＝`min(200K, 0.6 × H)`。** 这是成本和注意力的目标，不是物理限制。到 T 就开后台压缩，压完在两轮之间换上；超过 T 照常发送，后台没跟上也不要紧。
- **两条线都从当前绑定的模型推。** 换模型就重算；Bot 配置里的 `context_limit` 是主人手动设的上限，压低 H。

| 模型窗口 | H（约） | T |
|---|---|---|
| 1M | 900K | 200K |
| 128K | 110K | 66K |
| 64K | 50K | 30K |

为什么不是一个数：一个数只能二选一。设成目标（比如 10 万），一个大的工具结果就逼出一次同步压缩，1M 窗口明明还空着九成；设成窗口，几十万的上下文才开始处理，每轮又慢又贵。

为什么用比例再封顶：小窗口的模型要留出整理的余地，所以 T 跟 H 成比例；大窗口时 0.6 × H 是几十万，已经过了「越满越慢越贵」的那个点，所以封在 200K。

## 工作记忆分三段

| 段 | 放什么 | 多久变一次 | 为什么这么切 |
|---|---|---|---|
| 前段 | 人设、内核规则、Link 说明、技能清单、记忆快照 | 主人动手才变，不是每轮变 | 供应商的前缀缓存只认完全相同的开头，不变就一直免费 |
| 中段 | 摘要块，覆盖旧历史 | 很少变 | 每改一次，从这里往后缓存全部失效 |
| 后段 | 最近几轮的原文，加上每轮的状态 | 每轮都变 | 要保真，模型得看清刚才具体发生了什么 |

三段不是按时间切的，是按「变的频率」切的。缓存逐字节比较，前面相同的部分一直命中，从第一个不同的字节往后全部重算。所以越靠前的东西越必须稳定，这不是风格要求，是物理约束。

分界线不在「重要不重要」，在「多久变一次」。前段的东西允许变，前提是变得稀少：装一个技能、加一个 Link、压缩一次，这类事一天碰不到一次，掉了缓存也在几轮内赚回来。反过来，几点钟、有哪些待批卡、记忆改了什么，是每轮都在变的，放前段就等于每轮都从第 0 个 token 重算。**每轮要变的东西，一律归后段。** 把它往前挪不会让它便宜，只会让它把后面一起拖下水。

## 压缩就是搬运

把后段最旧的一段搬到中段。搬一次要调模型做摘要，付一次钱；搬完之后这段就固定了，以后每轮只按摘要的大小付费，不再按原文大小付费。

剩下的规则全是这条主线的推论，分三组。

**怎么搬**

- **每次只搬新增的那一段。** 记着「已经被覆盖到哪儿」，下次从那里往后搬，到尾巴之前为止。一次压缩的成本只跟新增内容有关，不随历史变长而变贵。
- **旧块不重写。** 它已经在上下文里、模型已经看过了。改它，从这里往后全部掉缓存，压缩就从省钱变成花钱。这是这块原来最大的缺陷：每次自动压缩都从第 1 条重摘整段历史，再覆盖同一个摘要块。窗口 1M 时一次可能是七十万 token 的调用，而且压一次掉一次缓存。
- **块攒多了才合并。** 合并是唯一必须重写现有块的动作，代价最大，所以刻意少见。留着最新那块不合并，因为最近的历史需要详细。
- **合并不能跨空隙。** 手动压缩可能在中间留下没被覆盖的原文。跨过去合并会把那些原文标成「已摘要」，从此不再进上下文——内容被静默吞掉。
- **被盖住的旧块直接从状态里删掉。** 块只追加不清理，被取代的文本会一直留在 `state.json` 里，每次唤醒整份读一遍。
- **多个块按序号归并着发，不能先发摘要再发原文。** 块本来就可以互不相交（覆盖 1–10 和 20–30，中间 11–19 留空），这是手动压缩的正常结果。所以组装要把摘要块和原文行按起始序号合到一起排：先输出所有摘要、再输出所有原文，会把中间那段空隙里的原文排到后面那个摘要之后，模型看到的时间线就错了。回归用例 `TestProjectedKeepsSequenceOrderAcrossBlocks` 守这条。

**怎么排**

- **只有一条时间线，摘要块就是这条线上的压缩段。** 发给模型的消息按序号单调递增，任何时刻都能指着一条消息说「它在第几号之前」。摘要块不是另一条线，它占住 [from, to] 这一段的位置。
- **空隙就是空隙。** 两个块之间没被覆盖的原文，照常按原样发在它们之间。不为了「整齐」把它并进任何一边——并进去就成了静默吞内容。
- **合并只在相邻处做。** 合并的前提是两块之间没有空隙，跨空隙合并等于把空隙里的原文吃掉。

**多块的现状（2026-10-19 实测）**

摘要块的存储与校验本来就允许多块，不是「只能叠一层」：

| 情况 | `blockOverlap` 结果 |
|---|---|
| 已有 1–10，压 11–20（相邻） | 允许 |
| 已有 1–10，压 20–30（隔开） | 允许 |
| 已有 5–10，压 1–20（包含它） | 允许，旧块被新块盖住 |
| 已有 1–10，压 1–10（完全相同） | 拒绝 |
| 已有 1–10，压 5–15（部分重叠） | 拒绝 |

所以「分别压 1–10 和 20–30」是支持的，`ActiveBlocks` 只剔除被更宽块覆盖的那些，互不相交的块共存。真正坏的是**组装**：见下一节。

**再压一次怎么算（已有 1–10、20–30，11–19 是原文）**

| 想压成 | 结果 | 之后的工作集 |
|---|---|---|
| 1–30（吃掉空隙和两块） | 允许 | `[1–30]` |
| 1–19（扩边界，盖住 1–10） | 允许 | `[1–19] [20–30]` |
| 11–19（只补空隙） | 允许 | `[1–10] [11–19] [20–30]` |
| 1–20（切进第二块一格） | 拒绝 | — |
| 5–25（部分重叠两块） | 拒绝 | — |
| 20–30（与现有完全相同） | 拒绝 | — |

规则一句话：**新范围要么完整覆盖旧块，要么完全不碰它，不能把一个块切开。**

- **覆盖时旧摘要不丢，它变成了新摘要的输入。** `summarize` 把落在新范围里的旧块文本放进 `prior`，所以压 1–30 的输入是「旧摘要 A + 旧摘要 B + 原文」，不是把已经压过的原文再读一遍。成本随摘要大小长，不随原文大小长。
- **扩边界的代价是从新块起点掉一次缓存。** 这是合并的必要开销，设计里已经认了：合并是唯一必须重写现有块的动作。
- **自动压缩永远不产生空隙。** `compactFrom` 找的是首尾相接那一串的末端，停在空隙之前，下一次从空隙处接着压。所以空隙只可能来自手动压缩——这也正是组装顺序 bug 的触发条件：主人手动压过中间一段，之后才会有「有块、有空隙」的状态。

**什么时候搬、搬多少**

- **越早搬越划算，但一次不能搬太多。** 一次摘要的钱要摊到后面很多轮上才划算；可单次调用贵，同步压缩时这一轮还得等它回来。所以到软目标 T 就在后台压，压完在两轮之间换上新摘要，不占这一轮的时间；只有逼近硬上限 H，才在轮内同步压。
- **尾巴要有大小上限，不能只按条数。** 后段是「还没搬的」。几条大的工具结果就能占满整个预算，只按条数留会把上下文顶在上限之上、又没有内容可压。尾巴上限和合并阈值跟 T 走：它们管的是成本和细节，不是会不会被拒。
- **做决定用校准过的数。** 估算对中文偏低约四分之一。每轮都有供应商上报的真实 prompt 用量，拿它算一个滑动比例修正估算；离 H 越近越要用真实数，没有上报时用估算加余量。

**怎么让人知道**

- **给模型的用量提醒按硬上限算。** 软目标是内核自己的事，后台会处理，模型不用操心；模型要知道的是离被拒还有多远，好少读大文件、少要大输出。拿窗口当分母也不对：窗口没扣输出预留和工具定义，提醒会来得太晚。
- **给主人看的面板两条线都画。** 色带上标出 T 和 H，说清「后台在整理」和「快到上限了」是两种状态。

具体数值（输出预留、估算余量、尾巴比例、合并阈值）落地后写在 [atlas/context.md](../atlas/context.md)，改它们不需要改这份设计；T 的封顶 200K 和比例 0.6 是主人定的，改它们要新的 ADR。

## 状态就是取代

压缩管的是历史。历史只增不减，所以只能搬。工作记忆里还有另一半：**状态**。现在几点、有哪些待批卡、记忆改了哪几条、后台任务结束了没有。这类东西每轮只有一个当前值，旧的当场作废。

状态不能按历史对待。按历史对待就会变成：每次变化追加一条，旧的原样留着。于是几十条「现在」堆在上下文里，模型得自己判断哪条算数。这不是省钱的问题，是判断力的问题。

三条规则，也是一条主线的三个推论——**状态只在变化时发一次，发出去就声明它取代之前那份。**

**只发当前值**

- **值没变就一个字都不发。** 拿这次的渲染结果跟上次发出去的比，一样就不发。时间戳尤其明显：同一分钟里连着几轮唤醒，「现在几分」不该重复出现。
- **变化了就发在尾部，不回头改前面的。** 旧的那份留在历史里不动——它已经命中缓存，改它才是浪费。新的一份追加在最后，模型看到的是最新的。

**发的时候说清它取代什么**

- **每份状态自带一句「我取代之前所有同类快照」。** 新旧并存时，这十几个字决定模型读哪一份。少了它，模型只能靠位置猜；位置这回事，它经常猜错。
- **清空也要说。** 状态归零（没有待批卡了）不是一个字都不发——那和「没这条规则」在上下文里长得一样。发一句「之前那些不再适用」。

**边界不能让外部内容伪造**

- **提醒要有闭合标签，进来的外部文本要转义标签。** 磁盘改动、工具输出、别人发来的内容里可能出现一样的闭合标签。不转义，它就能提前结束提醒、把自己变成指令。这一条不是格式洁癖，是权限边界。

## 提醒是独立的一条

状态之外还有一类东西：**某件事发生时的通知**。磁盘上的文件变了、后台任务结束了、熔断器要你换个做法、待批卡还挂着、任务清单发霉了、上下文过了一半。它们不是当前值，也不是对话内容，而是「此刻该知道的一件事」。

这类东西归一个通道，叫提醒。任意事件都能往上挂，挂上去就进上下文。

**一条提醒是独立的一条消息**

现在是贴在最新消息末尾的（`agent.AttachReminder` 直接 `last.Content += "\n\n" + text`）。改成独立一条：

- 模型看到的是一条完整的、有边界的东西，不是从别人的句子后面接上来的尾巴。
- 转义只需要在一处做：整条正文过一遍，外壳永远干净。
- 判断「这条是不是主人真说的」只需要看一个标签。现在 `status.go` 和 `reply.go` 各自维护一份标签前缀列表，加一种提醒要改两处；`reply.go` 那份还是安全判断，漏一处内核文本就被当成主人的指令。

**但它不占 transcript 的行**

这是改成独立一条时唯一的真问题。xbot 的 `seq` 和 transcript 的行一一对应，`reply_to`、`expand`、压缩范围全挂在这个对应关系上。提醒如果真落一行，行号和序号就错开了，三处一起坏。

所以**独立成条指的是组装时多出来的消息，不是存储里多出来的行**：

- 提醒照旧写在 `reminders.jsonl` 这个旁挂文件里，按它锚定的 seq 存；
- 组装时，锚在那条行上的提醒合成成独立消息，排在它的**后面**；
- 下一轮唤醒重新合成一次，字节和上一轮一致，前缀缓存照旧命中；
- 回放逻辑（现在把文本拼回原消息）改成合成独立消息，`Apply` 和 `Replay` 两处落点不变。

这条路已经有一条走通的先例：项目指令（`project` 这种提醒）现在就是这么做的。`Replay` 遇到它就单独追加一条，不让它拼进主人的原话，注释写明理由是「免得下一轮唤醒又把它塞回主人的可信文本里」；`Replay` 的返回值本来就允许比传入的行更多。要改的是把这条特殊照顾推广成默认。

**一个外壳，种类作属性**

```text
<system-reminder kind="file_change">
…
</system-reminder>
```

八种提醒现在各用各的标签（`<file_change>`、`<todo_reminder>`、`<todo_gate>`、`<background_done>`、`<project_instructions sig=…>`、`<context_usage level=…>`、`<pending_approvals>`、熔断那条才是 `<system-reminder>`）。收敛成一个外壳，种类放属性里：

- 展示层和信任判断只认 `<system-reminder` 一处；
- 加一种提醒不用再动那两个过滤表；
- 正文里出现的闭合标签统一转义，外部内容伪造不了边界。

**触发源自己注册**

现在八种提醒硬写在 `reminderKindsFor` 里，加一种必须改内核。改成谁要发提醒谁注册：注册时给一个 kind 名、一个冷却时间、一个「现在该不该发」的函数。内核只负责调度、去重、持久化、合成消息，不认识具体的提醒种类。

## 搬走不等于丢

这是整套设计能成立的前提，也是最容易被误解的地方。被压缩的内容：

- 原文一直在磁盘上，只追加，不改；
- `expand` 按序号读回全文；
- `recall_history` 用全文索引搜；
- `xbot export` 导出。

所以压缩是把内容从「在场」降级为「可找回」，不是删除。代价是模型得主动去查才知道，这也是摘要要保决定、名字、路径和没做完的事的原因。

## 做不到什么

- **摘要必然丢细节。** 压过的原文，细节只能靠 `expand` 取回，不会自动回到上下文里。
- **估算不是真 tokenizer。** 按 4 字节一个 token 估算。一个汉字在 UTF-8 里是三字节，算作 0.75 个 token，实际约 1 个，全中文的会话会低估约四分之一。校准数据已经在记（每轮上报的真实 prompt 和估算值都进轨迹），还没拿它做修正。
- **合并要掉一次缓存。** 这是有意的取舍：宁可偶尔掉一次，也不让摘要块无限长。
- **同步压缩会在轮内等。** 只有后台没跟上时才走这条，会有一次明显的延迟。

## 还没做的

按「状态就是取代」那三条规则对照，有两处不合：

- **状态类的东西还在按历史写。** `<environment_update>` 是追加成一条聊天记录的，时间精确到分钟，于是上下文里会同时躺着很多条「现在几点」。该改成只发当前值、变了才发、并带上取代声明。
- **技能清单和人设捆在同一条消息里。** 技能清单不该每轮变，留在前段是对的；问题是它跟 link 清单一起拼在第 0 条消息上，和人设、规则、overlay 挤在一起。装一个技能或 Link，整段前缀重算，人设那部分也跟着白算。该拆成独立的一段：动它只从它自己那里开始重算。拆完要实测一次缓存命中率的变化，别按直觉改。

按「提醒是独立的一条」对照，四处都没做：

- **提醒还贴在消息末尾。** `agent.AttachReminder` 就一句 `last.Content += "\n\n" + text`。该改成组装时合成独立消息，锚在原来那条的后面，不落 transcript 行。
- **外壳不统一。** 八种提醒七个标签，只有熔断那条用 `<system-reminder>`。该收敛成一个外壳，种类作属性。
- **两个过滤表各自维护标签前缀。** `status.go:99` 和 `reply.go:82` 各一份。`reply.go` 那份是安全判断，判定这条 user 消息是不是主人真说的。
- **没有转义。** `<file_change>` 的正文来自磁盘 diff，`<pending_approvals>` 来自工具参数摘要，都能伪造闭合标签。

再加一条结构问题：八种提醒硬写在 `reminderKindsFor` 里，加一种就得改内核。

两条线（[ADR 0015](../adr/0015-soft-target-hard-ceiling.md)）、轮内守线、超长重试和用量校准已经落地，现状见 [atlas/context.md](../atlas/context.md)。压缩这边还差：

- **轮内省略的是信息，不只是字节。** 真实 DeepSeek（30K 上限，一轮读 10 个大文件再总结）跑通了，请求一直在 20K 以下，但前 6 个文件的结果被省略后，模型如实说「没读到」。占位改成指向 `expand` 之后，内容装得下的任务（读 4 个文件再问第一个里的细节）模型会自己 `expand` 取回、答对；内容本来就是窗口三倍的任务，取回也装不下，模型停下来问主人。「先读完再总结」这类任务，省略前先摘要一次可能更好：多一次模型调用，换来不丢内容。要用真实任务比较之后再定。
- **跨轮的旧工具结果。** 轮内的已经会省略；已经结束的轮次里，大结果只在逼近 H 时才省略，平时靠摘要。可以更早省略，比摘要便宜，不用调模型。
- **空闲压缩。** 在缓存过期前、主人不在的时候提前压，别让压缩占掉等待时间。

- **Claude Code 走的是另一条路，值得知道但不要照抄。** 2026-10-19 反汇编本机 2.1.292 的结论：摘要始终只有一份，`pi()` 从最后一个 `compact_boundary` 起把数组截断，之上的一切（含更早的摘要和更早的原文）在组装前就丢了；没有区间字段，`compactMetadata` 只有 `messagesSummarized` 这种计数，保留段用 UUID 加 `parentUuid` 单链表表示顺序。所以它天然不会有「多块 + 空隙」这种状态，也就不需要处理组装顺序。
  - **为什么不能照抄：它的压缩是「另起一段」，我们的是「增量累加」。** 只留一份摘要意味着每次压缩都要把旧摘要连同新内容整体重写，那正是这次改造要除掉的东西——一次调用可能七十万 token，而且每压一次掉一次缓存。Claude Code 敢这么做，是因为它把切下去的原文真的不要了；我们的目标是「回头问第 1 轮的事实还答得出来」，靠的正是多块各管一段再加 `expand`。
  - 它有一处结构值得留意：除了 `compact_boundary`，还有 `microcompact_boundary`，那个边界不触发截断，只作渲染标记。说明「并存的、不同层级的边界」是有先例的。
