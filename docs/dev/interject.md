# 忙时插进新任务

> **30 秒版**：子代理在跑任务 A 时，用户在网页上又交代一件新任务 B。做完的样子是：B 发出后 3 秒内就有它的子代理记录（在跑或排队），A 不停、不重跑，A 和 B 的结果在对话里各报一次；连插 5 个也一样，每插一个前台最多多调 3 次模型。现在的内核已经能在 3 秒内答一句插话，但还没有测试测过「插进来的是新任务」，而且有两处会出问题：同时在跑的子代理到 3 个后，再派就直接报错；前台不知道哪些子代理在跑。第一步只写测评、测出基线，不改代码。

本文挂在「忙时插话」这条旅程上（`docs/guard/六条基本旅程.md` 第 2 条），做的是 ADR 0016 的第一步。范围只到网页：终端 `xbot chat` 的插话还走收件箱，不在这一步。

## 做完是什么样

贯穿全文的例子：用户先说「把 shop 仓库的测试全修了」，前台派出 A（开发类）。A 还在跑，用户又说「顺便查一下 Go 1.24 改了什么」，这就是 B（调研类）。

| # | 指标 | 假模型 | 真前台 |
|---|---|---|---|
| 1 | B 发出 → B 的子代理在任务列表里有记录（`running` 或 `queued`） | p95 ≤ 3 秒 | p95 ≤ 6 秒 |
| 2 | B 发出 → 这条请求的流里出现第一条可见输出（工具行或文字） | ≤ 3 秒 | 只记录，不设门槛 |
| 3 | A 不受影响：子代理 id 不变，状态一直是 `running`，没有被取消或打断，A 的子代理模型调用次数和不插话时一样 | 全部满足 | 全部满足 |
| 4 | 结果不丢、不重复：A 和每个 B 的结果都在 transcript 里以 assistant 身份出现恰好一次；之后再观察一个完整的 serve 周期（15 秒）也不多出来 | 全部满足 | 全部满足 |
| 5 | 连续插 5 个新任务（每 2 秒一个），每个都满足第 1 条；超过并发上限的进队列，不报错；最后全部完成并各报一次 | 全部满足 | 全部满足 |
| 6 | 成本：每插一个 B，前台模型调用 ≤ 3 次 | 全部满足 | 全部满足 |
| 7 | 成本：每插一个 B，前台 prompt ≤ 6 万 token，其中没命中缓存的 ≤ 1.5 万；一次完整真跑（A 加 5 个 B 加 6 次转告），前台合计 ≤ 50 万 token | 不适用 | 全部满足 |

这些数字的来由：

- **3 秒**沿用旅程里已有的「插话的回复 3 秒内开始出现」。假模型每次调用先等 300 毫秒才吐第一个字（`e2e/smoke/stub_test.go` 的 `stubFirstDelay`）。派出 B 要两次前台调用，一次调 `dispatch`，一次回话，所以模型本身占不到 1 秒，剩下的时间都留给内核。超过 3 秒，就说明内核里有地方在排队或在等锁。
- **6 秒**来自 xbot-dev 的真实记录（`~/.xbot-dev/bots/*/trace.jsonl`）。前台一次调用的 prompt 是 7 千到 2.1 万 token，相邻两次调用之间约 2.4 秒（那次输出了 331 个 token）。派出 B 要两次调用，约 5 秒，再留 1 秒余量。M1 用真前台测出基线后，按实测值改这个数。
- **5 次**沿用 `TestDispatchKeepsTheForegroundFree` 连发 5 句的做法。A 加 5 个 B 一共 6 个子代理，超过了并发上限 3，所以一定会走到排队这条路；又没超过排队上限 8（`internal/exec/exec.go` 的 `maxWaiting`）。
- **3 次调用**：正常情况是 2 次。前台工作角色 `chat` 的上限是 4 次（见 `docs/atlas/subagents.md`），所以给 3 次，留 1 次余量给「先读一个文件再派」。
- **6 万和 1.5 万**：3 次调用，每次 2 万 token，就是 6 万。真实记录里新开一轮时，第一次调用约 1 万 token 没命中缓存（18545 里命中 8448），所以每个 B 的未命中给 1.5 万。

B 进来时，前台可能处在四种状态，测评每种都要覆盖：

| 前台在干什么 | 现在的机制 | 预期 |
|---|---|---|
| 空闲，只有 A 在后台跑 | 直接开一轮 | 达标 |
| 正在等模型（比如刚派出 A，回话还没生成完） | ADR 0017：取消这次调用，带上 B 重发 | 达标 |
| 正在转告 A 的结果 | 同上，但这一轮的输出流会换给 B 的请求 | 没测过，要测 |
| 正在跑慢的只读工具 | ADR 0017 决定等工具跑完 | 已知会超过 3 秒；只记录基线，修不修见文末第 2 个问题 |

## 现在离目标差多少

### 已经有的

- **插话直接进正在跑的一轮**：`internal/kernel/interject.go` 的 `Interject` 把用户的话放进 `t.inter.queue`；如果有正在进行的模型调用，就通过 `preempt` 记下的 `stop` 取消它。之前那条请求收到 `OnHandoff`，答复改流到新的请求。
- **插话 3 秒内回复**：`e2e/smoke/interject_test.go` 的 `TestInterjectMidTask` 测了两种情况：子代理在跑时插一句，前台在等模型时插一句。它检查了首字少于 3 秒、长任务只调用一次模型、只有一条子代理记录、结果只报一次。但插进去的都是**问句**，不是新任务。
- **派活后前台空着**：`internal/web/dispatch_web_test.go` 的 `TestDispatchKeepsTheForegroundFree` 测了 3 步以内派出，派出后连发 5 句、p95 少于 3 秒。同样只测问句。
- **同一个仓库的开发任务排队**：`internal/exec/exec.go` 里 `Local.Start` 碰到资源被占（`busyLocked`）时，把任务写成 `queued` 放进 `waiting`；`launchLocked` 在前一个任务结束后接着起下一个。有 `TestSameResourceQueues` 和 `TestDevSubagentsOnOneDirectoryQueue` 测着。
- **结果当场送到**：`internal/kernel/agents.go` 的 `forwardExec` 把 `done`/`failed` 投进收件箱，再通过 `SetWaker` 注册的回调叫醒 Bot；`progress` 不进主线。
- **派活评测**：`evals/dispatch` 有 4 条真模型用例，`internal/eval/dispatch.go` 的 `recordExec` 只记录派活、不真跑。
- **用量记录**：每次模型调用的 prompt、completion、cached 都写进 `trace.jsonl`（`internal/kernel/usage.go`）。`e2e/longrun_test.go` 的 `measureCompactCost` 是按调用分类统计成本的现成写法。

### 缺的

1. **没有测试测「插进来的是新任务」。** 现有的两条测试都只检查插话有没有回复，不检查 B 是不是几秒内被派出、是新起了一个子代理而不是被当成对 A 的补充（steer）、A 有没有因此被取消。
2. **并发满了就报错，不排队。** 派活模式下，执行器的并发上限是 `forkCap()`，默认 `defaultForkCap = 3`（`agents.go` 的 `ensureExec`，常量在 `bgturn.go`）。`Local.Start` 只在资源被占时排队；资源不冲突但已经有 3 个在跑时，直接返回 `exec: max concurrent subagents (3)`。调研类没有资源，所以 A 加两个 B 之后，第三个 B 一定失败。
3. **前台看不到正在跑的子代理。** 每轮开头注入的 `backgroundNote(k.Backgrounds())`（`kernel.go`）只列分叉产生的后台轮次。`k.bgs` 只在 `bgturn.go` 分叉时写入，`dispatch` 派出的子代理不在里面。前台只能从 transcript 里那行「dispatched sa_… as dev」推断 A 还在跑；这一段被压缩之后就推断不出了，可能重派一个 A，或者把 B 当成对 A 的补充。`DispatchRule` 要求「同一件事不要起第二个」，但没给它列表。
4. **B 撞上 A 的转告那一轮，没测过。** A 做完后叫醒 Bot 开一轮转告。这时 B 进来，`Interject` 会把这一轮的输出流换给 B 的请求。A 的转告是会照样写进 transcript，还是被 B 的回答盖掉，现在没有测试证明。
5. **前台跑慢工具时会超过 3 秒。** 这是 ADR 0017 选择的结果（不打断正在跑的工具），旅程和候选卡「慢工具时插话 3 秒回应」都记着。
6. **没有成本口径。** 没有测试统计每次插话多花了几次前台调用、多少 token。
7. **网页上没有子代理卡片。** 结果回来时只有前台那一句话（候选卡「子代理类型」的「还没做的」一节）。

## 测评怎么写

分三层。只有第一层进门禁，后两层花真钱，手动跑。

### 第一层：假模型端到端（主力）

- **位置**：新建 `e2e/smoke/busy_test.go`，测试名 `TestNewTaskWhileBusy`，build tag 用 `smoke`。直接复用现成框架：真的 `xbot serve`、真 HTTP 和 SSE，`StartStub`、`Start`、`Send`/`BeginSend`、`Agents`、`Transcript`，以及 `Enter`/`Release` 闸门。
- **替身脚本**：在 `stub_test.go` 里加几个标记。`SMOKE_TASK_A` 让前台派一个开发子代理，子代理停在闸门 `a`；`SMOKE_TASK_B1` 到 `B5` 让前台各派一个调研子代理，各停在自己的闸门。测试按顺序放开闸门，所以结果回来的顺序也由测试控制。
- **场景**：
  1. 前台空闲，插 1 个 B；
  2. 前台在等模型，插 1 个 B；
  3. 前台在转告 A，插 1 个 B；
  4. 连续插 5 个 B，每 2 秒一个；
  5. B 和 A 用同一个仓库：B 应该排队，前台回话里要说它在排队；
  6. 前台在跑慢的只读工具，插 1 个 B：只记录用时，不判过不过。
- **怎么量**：发出 B 时记一个时间，然后每 50 毫秒查一次 `Agents`，看到 B 的记录就停表，得到第 1 条；第一条可见输出的时间从 SSE 里读，得到第 2 条。模型调用次数和每次的请求体大小从 `stub.Requests()` 按调用方统计；token 按内核的估算口径算，约 4 字节一个 token。第 3、4 条照抄 `TestInterjectMidTask` 的检查：闸门只能由测试放开，模型调用次数、子代理记录数、转告次数都要恰好对上。
- **基线怎么记**：M1 把全部断言都写上。现在已知达不到的那几条放进一个 `baselineGaps` 表，只打印实测值、不判失败，这样其余六条旅程的门禁照样是绿的。M2 把这张表清空，所有断言就都生效了。按旅程的规矩，用例由不写实现的一方来写，实现的一方不改期望。
- **用时**：5 个场景之间不重启 serve，只最后观察一个 serve 周期，预计 2 到 3 分钟。单独跑用 `go test -tags smoke ./e2e/smoke/ -run TestNewTaskWhileBusy`；整套 smoke 会从约 5 分钟涨到约 8 分钟。

### 第二层：真前台、假子代理（手动）

- 还是同一个测试。设了 `XBOT_BUSY_REAL=1`，替身就把前台的请求转给 deepseek-flash，密钥只从环境变量读，不进日志；子代理和压缩的请求仍由脚本回答、停在闸门。这样花钱的只有前台，子代理不花钱，也不会真动文件。
- 用户的话里带编号（比如「查一下 Go 1.24 改了什么（编号 BUSY_B1）」），替身靠任务说明里有没有这个编号来认是哪个任务。真模型要是把编号丢了，就记一次「任务说明不全」。
- **控制成本**：替身累计前台的 prompt token，超过 50 万就不再转发，测试判失败。一次约 3 到 5 分钟，只在 M1 测基线和 M2 验收时各跑一次。

### 第三层：派活判断的评测（手动）

`evals/dispatch` 加 3 条：A 在跑时来了不相干的新任务，应该新派一个，不能 steer 或 cancel A；来的话是要改 A 手上的活（「A 那个顺便把 README 也改了」），应该 steer A，不能新派；B 和 A 是同一个仓库，应该照样派出，由内核来排队。用 deepseek-flash 跑 3 次，按现有口径要 pass^3 = 1.00。每条最多 3 次调用、每次约 1 万 token，3 条跑 3 次约 27 万 token。

## 风险和要拍板的

风险：

- 假模型测出来的只是内核本身的时延。真实时延主要看模型，所以第 1 条真前台的 6 秒要等 M1 实测后才算定下来。
- 真模型可能不把用户话里的编号写进任务说明，这样第二层会判成任务没认出来。这本身也是真问题，但会让时延的数据断掉。

要政东拍板：

1. **排队算不算「派出」？** B 和 A 碰同一个仓库，或者同时在跑的已经有 3 个时，B 会进队列，不会马上开始跑。我建议算：B 有了记录，前台也说清楚它排在谁后面，就算派出。并发上限保持 3，不往上调。
2. **前台跑慢工具时超过 3 秒的问题，这一步修不修？** 我建议这一步只测出基线，不修。要修就得推翻 ADR 0017 的「不打断工具」，最好单独写一份方案。
3. **真模型的预算。** 第二层每次最多 50 万 token，只在 M1 和 M2 各跑一次；第三层每次约 27 万 token，跑 3 次。可以吗？
