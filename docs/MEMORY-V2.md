# 记忆 v2 规格

2026-10-17 主人批准。决策见 [ADR 0008](adr/0008-memory-v2-dated-log-first.md)；现行记忆设计见 [atlas/memory.md](atlas/memory.md)，本规格落地一批，atlas 就更新一批。本文是过程快照，定下来就冻结。

## 结论
- 骨架不动：两层范围（person 和 bot，[ADR 0006](adr/0006-two-memory-scopes.md)），两级存储（常驻 profile 和检索日志），每个范围的 profile 上限 4 KiB。
- 补齐七个细节：
  - 常驻记忆带日期；
  - 渲染去掉重复的 key；
  - 注入时显示用量；
  - 常驻最近 8 条日志；
  - 按唯一子串改写条目；
  - 日志按月分文件；
  - 自动写经过摘要。
- 最后加每晚整理、Grok 导出导入和 `xbot backup`。
- 共 6 批，每批不超过约 500 行。

## 1. 参照：对照了什么
我们对照了两样东西：主人自己的 Grok Bot 数据导出的形状，以及那个产品的外部可见行为；另外看了 Hermes Agent 的公开文档。下表右两列都是**观察或公开资料**，不代表任何一方的内部实现。

| | Grok Bot（导出形状与可见行为） | Hermes Agent（[公开文档](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)） | XBot（本规格之前） |
|---|---|---|---|
| 常驻 | 每个 bot 的 profile | `MEMORY.md`（2,200 字符）加 `USER.md`（1,375 字符），会话开始时注入 | person 和 bot 的 profile，各 4 KiB |
| 跨 bot 共享 | 有一个关于主人的共享层，条数远少于各 bot 自己的记忆 | 每个 profile 各有一份，不共享 | person 层共享 |
| 流水 | journal，按查询召回，有条数上限，长条目截断，并提示"另有 N 条未展示" | 没有 journal，用 `session_search` 检索原始会话 | log 和 `recall_history`；`recall` 前 20 条，不提示有没有漏 |
| 日期 | 每条带日期；可以看到改写过的条目保留了首次写入的日期 | 不带日期 | 存了时间，但常驻和检索都不显示 |
| 改写 | 可以看到条目被原地改写 | `patch`/`remove` 按唯一子串定位 | 只能按全文 forget，再重写 |
| 写满 | — | 报错；提示头显示用量百分比 | 报错，提示整理 |
| 自动写 | 有"经过摘要"类条目 | 每轮结束后后台复盘 | 压缩前抽事实 |
| 坏味道 | 过时事实靠"（已过时）"注记；profile 里混进单日流水；记忆被拿来当去重状态表 | — | 不给 key 时 key 就是正文前 80 字节，于是每条渲染成"同一句: 同一句" |

## 2. 能力清单
| 能力 | 状态 |
|---|---|
| 常驻每条带日期、按时间倒序；key 与正文重复时只出正文；每个范围显示用量，如 `Bot（2.7/4 KiB，67%）` | 设计内（批 1） |
| `recall` 每条带日期，末尾写"另有 N 条匹配未显示" | 设计内（批 1） |
| `update(match, fact)`：`match` 是唯一子串，原地改写，保留首次写入时间，记录更新时间；匹配到多条就报错，要求给更长的子串；`forget` 同样接受唯一子串 | 设计内（批 2） |
| `remember` 省略 tier 时写日志；profile 只放每次对话都用得上的稳定事实 | 设计内（批 3） |
| 每次唤醒常驻 bot 最近 8 条日志，预算约 1.5 KiB，单条截到约 200 字，末尾写"日志共 M 条，更早的用 recall"。不注入 person 的日志 | 设计内（批 3） |
| 日志按月分文件 `journal/YYYY-MM.md`，每个文件不超过 64 KiB；`log.md` 和 `log.overflow.md` 自动迁移，原文件改名留作备份；`recall since=` | 设计内（批 4） |
| 压缩时多写一条经过摘要：一句话，不超过 300 字，用主人的语言，同一天按文本去重 | 设计内（批 5） |
| 每晚整理：把 profile 里的流水降回日志，合并重复，改写被取代的条目，把 profile 改成固定几段的工作档案；直接改，每次改动的 diff 记成一条日志，可以回滚；本地时间运行，错过不补跑，当天没有新写入就不跑；person 层只降级和去重 | 设计内（批 6） |
| `xbot memory import <导出.md>`：把"(日期) 文本"按 profile 和 journal 导入；`xbot backup`：不带保险箱、`secrets.json`、`web-token.json`，聊天记录可选 | 设计内（批 7） |
| 自带技能目录：随二进制分发、只读，用户技能盖过它；`read_skill` 加参数可读 `references/` 下的附件 | 设计内（桌面端 B 阶段） |
| 项目范围 | 不做：只留两层，项目知识放 AGENTS.md、atlas 和 docs |
| 按写入者分目录 | 不做：`by` 字段已经够用 |
| 把记忆改写成第三人称英文 | 不做：保留主人原话的语言 |
| 关键词自动召回 | 不做（见 CANDIDATES）。最近 8 条是按时间固定注入，和本轮聊什么无关，不算自动召回 |
| 拿记忆当去重状态表、单日流水进记忆 | 不做：这类状态写进 bot 的工作文件；MemoryRule 写明这条规则，并配一个评测用例 |

## 3. 关键决策
- **默认写日志，常驻最近 8 条**：profile 默认就写，4 KiB 很快写满，而且混进流水。改成默认写日志之后，近期上下文靠"最近 8 条"补上，profile 只留稳定事实。注入预算从 `2×4KiB+512` 变成 `2×4KiB+1.5KiB+512`。
- **按唯一子串定位，不加 id**：不改文件格式，PR 更小。真的出现子串冲突，再考虑加 id。
- **矛盾的事实靠日期解决**：冲突规则不变，系统不替模型判断两条没有 key 的事实谁对谁错。显示日期，让模型自己取新的。
- **每晚整理直接改，留 diff**：这样不用主人逐条审批，可以回滚，整理后仍受 4 KiB 上限约束。

## 4. 实现批次（dsh 写，zcode 独立审查；每个修复都配一个在旧代码上会失败的回归测试）
| 批 | 内容 | 通过条件 |
|---|---|---|
| 1 | 常驻带日期、倒序、去重 key、显示用量；`recall` 带日期并提示"另有 N 条" | 渲染测试；`memory-scope` 评测不退步 |
| 2 | `update` 工具；`forget` 支持唯一子串 | 子串唯一、多条、零条三种情况都有测试；评测"把目标从 80 改成 78"不产生重复条目 |
| 3 | `remember` 默认写日志；常驻最近 8 条 | 评测：全新会话问"昨天定了什么"，不调 `recall` 也答对 |
| 4 | 日志按月分文件和迁移 | 迁移跑两次结果一致；拿线上日志的副本迁移，条数不丢 |
| 5 | 经过摘要 | 压缩后 `recall` 能找到当天的摘要，且不重复写 |
| 6 | 每晚整理（可拆成两批） | profile 不超过 4 KiB；diff 已记进日志并能回滚；工作档案评测 |
| 7 | 导入和备份 | 导入一个真实导出后条数和日期都对；备份包里没有密钥文件 |

排期：批 1–3 放在晚上的时段做，批 4–6 在 11/30 迁第一个真实 Bot 之前完成，自带技能目录放在桌面端 B 阶段。
