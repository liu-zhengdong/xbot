# 生态：Link、MCP、技能、连接器、编码代理

> **30 秒版**：MCP 经当前实例 CLI 进入每 Bot 的进程资源，同一会话负责发现、调用和通知；模型请求不带 MCP schema。浏览器与 Telegram/飞书等非 MCP Link 仍经工具注册表和 `tools` 门，用户技能与编码代理保原器官。连接应用设置和 `links` 继续管理目录/安装，MCP 的实际入口见 [ADR 0047](../adr/0047-mcp-cli-domain-entry.md)，非 MCP 工具门见 [内核](kernel.md#工具注册与代理门)。

例程CRUD沿当前source实际cached Timer的CLI，不再登记四个例程模型门；研究型只读允许list/help，源审批桥及JSON/人读双32KiB完整产物规则见 [内核](kernel.md#例程实例与原调用审批)。例程可用 `skills` 按序引用本库技能；叫醒时沿共享 id/停用解析器读取，保原单项16KiB投影，正文仅供当轮请求，缺失明确跳过。CLI runtime read 则返回有界完整正文或本地产物。字段写口与唯一装配缝见 [多 Bot](multibot.md)「例程挂技能」。

## 边界
负责：各类 Link 的接入方式。不负责：确认规则（见 [安全](security.md)），各片进度（见 [MILESTONES](../MILESTONES.md)）。

## 怎么运转
- **当前实例 CLI 身份**：主线、dev/general scoped Shell 和本机编码任务在最终进程环境缝共用当前 `XBOT_BIN`、规范 `XBOT_ROOT`、`XBOT_ENDPOINT` 和诊断 `XBOT_BOT`，覆盖父进程残留身份；外部编码命令仍保留原基础变量白名单与供应商密钥剔除，内置编码 Shell 走同一绑定。`XBOT_BIN` 是活实例二进制绝对路径，不代表系统 PATH 已安装 xbot。可写本机子代理和编码任务晚于父 serve.Pass 结束时，原 live 集合维持入口至实际完成；research 仍按原只读命令分类，不把任意 xbot 当 readonly，远端 runner 尚无回连通路。改名后原 endpoint 继续识别同 Resources 的当前 Bot，后续 Shell 在当前路径装配 cwd/身份，不凭旧 `XBOT_BOT` 重新定位。组合资料 set 与独立头像动作见 [多 Bot](multibot.md#运行时普通资料)；role/预算及其它 CLI 族不随此扩展。
实际agent Shell在最终ctx-aware环境缝另带本次真实Job的XBOT_CALL_ID；仅非空routine precheck及strict Bot Delete通过可选header关联原live ctx/approver，结束清除，继承旧CallID剥除。编码任务/remote没有这条原执行审批上下文，不能冒认另turn；无precheck例程、permissive Bot管理与资料/MCP/技能不强制此关联。Bot四typed操作沿原source（动态状态/host删除、primary与原owner范围），四模型门已退而其它peer/管理工具保留，见 [内核](kernel.md#bot-发现与管理实例入口)。

- **按解释器执行命令**：工具目录不注册泛用 `shell`。macOS 探测 `zsh`、`bash`、`sh`，Linux 探测 `bash`、`sh`、`zsh`；Windows 探测 `powershell`（优先 pwsh）、`cmd`，以及 Git 安装目录中的 `git-bash`。只挂载能找到的可执行文件；版本探测每个最多 1 秒、输出最多 512 字节，失败仍挂载并标「版本未知」，发现结果进程内缓存。描述注明解释器名和版本；调用必须带 `description` 说明目的（最多 1024 字节），命令仍限 16 KiB，原始参数限 128 KiB。主线、子代理、编码执行和 runner 共用这套发现；评测沙箱明确使用 `sh`。各壳复用现有权限、机器开关、cwd、Jobs、输出脱敏和取消机制；本机 `sudo -A` 走同一进程环境装配（见 [安全](security.md#保险箱与出站代理)），不加模型工具；任务记录保存实际工具名和用途。
- **原生内置 Link**：Shell 和文件（`read_file`、`write_file`、`edit_file` 受内核的文件新鲜度检查：没读过的已有文件不能改，读过之后被别人改了就拒绝写，见 [内核](kernel.md)）、浏览器（通过 CDP 驱动本机 Chrome，工具 `browser_open`、`browser_snapshot`、`browser_click`、`browser_stop`）、桌面操作、HTTP 请求（`http_request`）、公开网页（`web_fetch`、`web_search`）和看图（`view_image`）。内核挂上原任务表之后，所有工具共用慢调用生命周期，默认前台等 2 秒，插话立即让出；不取消实际运行，输出仍进 Bot 的 `shell-jobs/`，复用 `shell_output`、`shell_status`、`shell_cancel`，完成为普通 Inbox 回报。`timeout_seconds` 仅缩短 shell 的前台等待；未挂表的单独 shell 与评测沙箱仍沿原硬超时，详见 [内核](kernel.md)「慢工具后台化」。挂上会话之后，前台 `cd` 留在这个 Bot 上，结果带 `cwd:`；目录丢了或不在工作区里就回到工作区并写明。后台任务记下启动时的目录。文件工具和 `view_image` 的相对路径跟着调用方的目录走（前台、某个后台分支或某个子代理），绝对路径不变；解析符号链接之后必须还在工作区或共享目录里，沙箱里则钉在沙箱根上。`web_fetch` 只取公开的 http(s)，HTML 收成文字，重定向最多 5 次，超时 20 秒，正文超过约 48 KiB 截断；私网、回环、链路本地、元数据和 DNS 前后两次结果不一致都拒绝。`web_search` 默认使用 DuckDuckGo，无需密钥。全局网页搜索设置沿用 `web.json`：`search_enabled` 缺省为开，`search_mode` 缺省为 `auto`，`local` 表示强制本机；本机供应商仍在 `search.backend`。切换本机供应商只改选择，保留已有 DeepSeek 的密钥绑定和端点。设置页首次保存后以文件内选择为准，不再被旧的 `XBOT_SEARCH_*` 选择覆盖。`config.SearchProviders` 是九家名单的唯一来源；DuckDuckGo、DeepSeek 已实现，其余选择明确报不可用。DeepSeek 仍走官方 `POST /v1/tools/search`，不传模型。设置页校验沿用已配置的可信出口网段，仅向官方地址发送，成功后复用 `SaveEnvKey` 写入本机 `env`（0600、文件锁、原子替换），使用专属 `XBOT_SEARCH_DEEPSEEK_KEY`，不覆盖模型密钥；运行时直接读取专属条目，所以 `serve` 重启后也能使用，不依赖桌面入口加载环境。凭据读取、保存与脱敏登记共用同一文件锁，地址与密钥一次解析为一致快照。启动入口在任何工具可用前把全部已保存的搜索密钥加入现有持有及脱敏路径，包括未选中的供应商；密钥不回传前端。旧显式 `api_key_env` 与安全地址限制仍可用；使用设置页校验后的密钥一律发往官方地址。内核挂载一次动态搜索对象，调用时读取选择，已有 Bot 不需重启。DuckDuckGo 返回非 200 或挑战页时直接报错，让模型告诉用户，不说明怎么换后端。两者的结果都包在 `<untrusted_event>` 里。结束标签换成 `[/untrusted_event]`，不再留下还能被认成标签的形式；大小写、空白、全角、全角下划线、小写小于号、分数斜线、零宽字符、组合附加符号、形近括号（`‹›`、`〈〉`、`⟨⟩`、`«»`、`˂˃` 等，和记忆围栏用同一份）、数学和带圈字母这类兼容字形、形近的西里尔和希腊字母，以及 `&lt;/untrusted_event&gt;` 都会拆开。超长工具结果仍走 transcript 的 blob 和预览。`view_image` 接受 JPEG、PNG、GIF、WebP，文件超过 32 MiB 不读，超过 10 MiB 不送给模型，边长超过 2048 会缩小（WebP 超了就拒绝，读不出宽高也拒绝）。边长不超过 2048 的 JPEG、PNG、GIF 原样通过，不按解码后的字节数拒绝。要缩小的那一路才解码，一次解码最多按 160 MiB 估计（渐进式 JPEG 按每像素 12 字节，16 位彩色 PNG 按 8 字节，边长仍不超过 4096），解码一次只跑一张；WebP 不解码，不占这份额。模型看不看图写在模型条目的 `vision` 上：`deepseek-flash`（以及名字里同时有 deepseek 和 flash 的）默认能看，`deepseek-chat` 和 `deepseek-v4-pro` 默认不能；显式 `vision: true/false` 盖过默认。没绑定供应商时跟 `XBOT_MODEL`，不再写死 deepseek-flash。不能看的模型直接得到 `model <id> does not support vision`，不把图片悄悄丢掉。能看的模型在这一轮里收到 Chat Completions 的 `image_url` 数据 URL，只保留最新一批，仍是一轮最多 4 张、合计 10 MiB。图片字节不进 transcript，这一轮结束才从内存里清掉，下一轮没有。子代理连续调用工具时也只留最新一批，在没有工具调用的回复之后全部清掉，再接排队或插话。
- **MCP 实例 CLI**：协议 client、stdio/HTTP、诊断和配置在 `internal/mcp`，只依赖标准库与 fsutil；`BotResources` 提供领域方法，source/human HTTP 都调用它，provider predicate 显式注入。serve/chat 进程 Manager 持同 Bot/server 唯一真实 Session 与通知泵，K 借资源不关连接；热配置与引用凭据的真实变化只替换受影响 slot，坏外部配置保最后有效 spec，但仍检查其 auth 输入。有效输入不变、被 local 遮住的 global、同值/无关密钥/仅 domains 不重连。所有权见 [ADR 0046](../adr/0046-process-owned-mcp-sessions.md)。服务器登记在用户全局的根目录 `mcp.json`（所有 Bot 共用），Bot 自己目录里的 `mcp.json` 仍会读，同名时 Bot 的那条覆盖全局；字段是名字、命令、参数，以及密钥环境变量的名字。密钥的值不写进文件，也不进接口。拉起进程时不用 shell，环境只留一小份基础变量（`PATH`、`HOME`、`TMPDIR`、`LANG`、`SYSTEMROOT`），再加上这些名字的值：装配现读整机产品保险库，没有再用当前进程环境里的值；比较、子进程 env/HTTP headers 与启动诊断共用同一冻结引用输入快照，不另存值或摘要；旧 Bot 明文已迁入，不是运行回退。配置 vaultd 时不绕过后端读本地明文；daemon 没有本机进程的明文导出。HTTP 把同名且已设置的非供应商密钥放进请求头。供应商 API key（`HoldKeys` 记下的名字，含 `XBOT_API_KEY` 和各 provider 的 `api_key_env`）不能写入 `secret_envs`，不进子进程环境，也不进 HTTP 头，并且不从内存里的 key 副本读出。传输有两种，协议版本都是 `2024-11-05`。stdio 是按行分隔的 JSON-RPC，拉起进程时不用 shell。Streamable HTTP 把 `url` 记在同一份 `mcp.json`：有地址就不再用命令。客户端 POST 一条 JSON-RPC，`Accept` 同时写 `application/json` 和 `text/event-stream`。JSON 响应压成一行再交给原来的读循环；SSE 只取 `data`。响应头 `Mcp-Session-Id` 之后每次都带上。`202` 空响应是通知，不当成失败。拿到会话之后对同一地址 GET 一条 SSE，用来收服务器主动发的通知；对方返回 405 就当没有这条流。两种都是先 `initialize`，再 `notifications/initialized`，然后 `tools/list`（跟着 `nextCursor`，最多 20 页）。实际调用走 `tools/call`，CLI 使用远端原名，不再注册 mcp_ 工具或模型 schema。research 的 `--readonly` 在同一次选定 slot/session 上精确查 hint=true 后重核并调用；换代不转发新会话。core 保完整 ToolSpec/annotations Raw 和 tools/call 未知数据。领域层回64KiB有界JSON、文本/本机图片与完整Raw/structured/unknown产物；image真实解码，resource_link不fetch。isError保内容输出而CLI非0，transport失败另报，不自动重试未知写结果。入站是可选的：`notifications/xbot/event` 和 `notifications/message` 的 `text` 写成来源 `mcp:<名字>` 的不可信事件；没有这类通知也可以。通知通道满了就丢掉，不能堵住工具调用；Manager 在热新增时直接接通知→原 Inbox→锁外 waker，不等 web/describe 预热。目录里的 `mcp` 条目仍然不能一键安装，因为一条授权没有命令可跑。另有一份打进二进制的连接器目录（JSON），不是托管市场。商店「已添加/已连接」必须表示鉴权后续已完成：目录声明了密钥就走设置内输入，声明了 OAuth 就走浏览器登录；未完成不得标已装（见 [ADR 0023](../adr/0023-connector-auth-followthrough.md)）。「一键」只省 CLI，不省凭证。`xbot connector list` 列出 id、传输、命令或地址、密钥名。`xbot connector add <bot> <id>` 把这一条抄进该 Bot 的 `mcp.json`，只启用这一个 Bot（重复添加不报错）；设置里的应用商店则写进全局 `mcp.json`，所有 Bot 下一轮都有。原生能力由 `link.Organs()` 同时驱动 CLI 启动和内核装配，开机即挂，不是商店卡，也不由 grant 控制；包括 terminal、tools、timer、memory、persona、context、agents、skills、webhook、watch、web、peers、desktop 和有本进程后端的 coding-agent。旧 `config.links` / `apps.json` 中的器官名读取时忽略；浏览器依赖本机 Chrome，是商店卡（`StoreApps`）。网页抓取目录行标 `retired`（已由原生 `web_fetch` 取代）：不在 `Connectors()` 里，商店、`links search/install` 都没有；旧 `mcp.json` 里同名条目不挂载，也不出现在 `/api/apps` 和已连接计数。系统提示里单独一块「连接器」，只列真正的 Link，每行 `名称:描述`，不放 MCP 的工具定义；工具经代理门 `tools` 的 describe 披露。`xbot connector remove <bot> <id>` 删掉。目录里没有密钥的值。`chat` 和 `serve` 都会把这些事件推进收件箱。`serve` 每一轮用来处理收件箱的内核是短命的，不在那上面再挂一条连接；第一次有服务器时另留一个长期内核来收通知。这一轮已经接上之后再改 `mcp.json`，要重新打开 `chat` 或重启 `serve`。
- **Bot 自己管理 Link**：内置工具 `links`，动作是 `search`、`install`、`remove`、`load`。`search` 查精选目录，中文摘要之外也匹配英文关键词和 id，返回 id、一行摘要和密钥的名字。`install` 每次都走用户的确认卡，和 shell 这类需要确认的工具同一条审批。这条 Link 如果声明了密钥，确认卡带上密钥的名字，用户在界面里填写值。连接器（Telegram、飞书）的 token 与 MCP 环境密钥全部写进 `vault.OpenGlobal(root)` 的整机产品保险库，都不进确认摘要，不进工具结果，也不进给模型的提示。没填齐就不安装。对话里的 `links install` 对目录应用（如 Context7）走这条：`id` 认目录 id、商店标题或 `mcp:<id>`，确认卡列出目录的 `secret_envs`，填齐后值写进全局保险库，再把这一行写进全局 `mcp.json`；全局里已有缺这些密钥名的旧条目时换成目录这一行。`remove` 删掉全局和该 Bot 的条目，以及全局保险库中的这些密钥；商店「移除」同样删除共享密钥。`search` 列出这些行，条目带齐密钥名、且每个密钥在全局保险库或进程环境里有非空值才算 installed；商店按拉起时的同一取法判断（先全局保险库，没有才看进程环境；存了空白不回落环境），每个密钥都非空才算已连接，只有名字不算。还没有运行时的条目，即使用户填了密钥，也不安装、不把值落盘。`remove` 也要用户确认，确认后同时删掉这条 Link 的密钥：统一用全局 `backend.Remove` 删。系统提示的「连接器」块只列商店类应用与自定义 MCP，每行 `名称:描述`，不放工具 schema；webhook/watch/skills/coding-agent 不在这个块，原生工具常驻，技能摘要仍单独列出。这一段大约 1KB；超了就只列 id，摘要用 `search` 查。非 MCP 的 `load` 返回工具 id，之后经代理门调用；MCP load 返回当前 CLI 指引。`install` 写上授权后同进程 reconcile，不用重启 `serve`，MCP 用 tools/describe/call 子命令发现和调用，配置保存不冒充 ready。终端的 `--yes` 不能代替用户填写密钥。
- **用户技能**：是常驻原生器官，不另起机制。每个数据根一份本机技能库，路径是该数据根下的 `skills/<slug>/SKILL.md`。格式和 `~/.agents/skills` 一样：YAML 头里 `name` 是 slug，可选 `title` 是人读短名（如「记一下」），`description` 是说明，支持 YAML 块标量；头部解析失败或无说明时说明为空，后面是 markdown；旧文件的可读 name 继续作为无 title 时的降级。`xbot skill import <path>` 把技能拷进本机技能库；源路径可以是符号链接。库里的目录如果本身是指向技能目录的符号链接，同样能列出来、能读。所有本机 Bot 都能看见这份库，包括无 owner 和多 owner 的 Bot。每个 Bot 用自己的停用名单关掉其中几条，不影响其他 Bot。聊天群不是 Bot，没有技能库。系统提示的 Skills 段只给运行时库目录、id/description 与当前 CLI 读法，用户技能盖过 Bot 默认习惯，约1KB超限只留名字。`skill read ID --self --json` 以原 source/ref 检查当前磁盘停用配置，按排序匹配 Slug 或 Name（Title不是ID）；所有候选以20MiB/max+1有界读取，HTTP硬上限64KiB，完整解析正文仅在整JSON含换行符合现Shell32KiB时内联，过长则完整脱敏正文存当前工作区 results 并给 preview/file/access:local/bytes，metadata超限明确报错。没有16KiB静默截断；例程仍保原16KiB政策，旧历史工具正文投影仍可读。`skill write SLUG --description TEXT --body TEXT|--body-file FILE|- --self` 创建或覆盖，完整序列化请求至多1MiB，Body缺失与显式空串不同，超限不截后写。可选 title 单行化安全引用；scope省略/空为全部本地 Bot，self为当前Bot，具体名字忽略大小写且包含不同owner/shared/orphan，真名global不被当保留字。--self只定位原endpoint，改名后仍认当前Bot。可预测校验和纯scope预检在业务写前，source route→现库锁→逐config锁覆盖文件与全部默认开关，同一赢家决定正文和defaults；之后手动开关仍权威。真实文件已写而后续config失败保written/updated_bots/error且非0；只合并实际开关字段，保未加载旧Bot的style及未知配置，不在route内触发Load/记忆迁移。read使用source配置SkillsDir，write保原root/skills目录差异，不替换其它source的配置。两旧模型schema、wrapper与load返回门均已退役，main/legacy/continuable使用原Shell入口；research仅共同窄lexer/纯parser准许的self read/help。离线list/show/import/remove/enable/disable语义保留，show仍原文件；具体合同见 [ADR0050](../adr/0050-skills-runtime-cli.md)。 设置页「技能」走库级接口列出和导入，导入由浏览器读出文件夹里的 SKILL.md 发来，同名要确认才覆盖，检查加写入在同一把锁里；开关仍是各 Bot 的 `disabled_skills`。删除出库（设置页或 `xbot skill remove <slug>`）在库写锁内先清掉所有 Bot 停用名单里的这个 slug，再删 `skills/<slug>/` 目录。见 [界面](ui.md#技能设置)。
- **旧技能迁移**：离线技能入口、内核打开和网页注册时按当前数据根迁移，runtime read/write 在本地迁移/配置初始化前分流，`~/.xbot` 与 `~/.xbot-dev` 分别处理。一级已有 `SKILL.md` 不作 owner 扫描；旧 `owner/slug` 整目录提升，保留辅助文件。冲突比较 `SKILL.md` mtime，较新者保留原 slug（同时间优先已扁平版本），其余为 `<slug>__from_<owner>`；原有扁平版本旁路时来源为 `local`，旁路重名加 `__2` 等后缀，不覆盖。操作路径追加至 `skills/.migration.log`，失败条目保留重试，其余继续；迁移和导入、runtime skill write 共用 `skills/.write.lock`。已完成的迁移重跑不新增备份或日志。
- **技能收成提议**：内核规则提示 Bot 在刚完成可复用的多步活且 Skills 列表没有等价技能时，说明用途和下次唤起方式，供主人确认、改名或拒绝；确认或主人明确要求后再执行当前实例 skill write CLI。空库也有这条规则；它是模型行为指引，没有新增代码级确认卡。
- **Link 插件市场**：上架的是实现 Link 协议的插件（出站工具 + 入站 Event），不是 MCP 市场。自定义聊天室、Telegram、飞书（Lark）这类连接器都可以上架，把外面收到的消息推进来，变成 Event。一份精选清单，默认不安装，点一下就添加。
- **连接器**：Telegram 和飞书。装上之后，外面的消息才进收件箱。安装要用户在确认卡里填密钥（`TELEGRAM_BOT_TOKEN`、`LARK_APP_SECRET`）。值存进整机全局保险库（`vault.OpenGlobal(root)`），名字是 `telegram.token`、`lark.token`，分别只绑定 `api.telegram.org` 和 `open.feishu.cn`；不进系统提示，不进 transcript，也不进工具结果。出站请求只带 `{{secret:telegram.token}}` 这类占位符，真值由保险箱的出站代理在请求离开进程时填进去（见 [安全](security.md)）。旧 Bot 密文及 `secrets.json` 明文在全局库第一次打开时安全合并；先检查全部冲突，再提交目标后删源。冲突策略与路径只在 [安全](security.md#保险箱与出站代理) 维护。命令行安装从同名环境变量读；变量是空的就不装、不落盘。网页 `POST /api/bots/{name}/links` 不接收密钥，声明了密钥的条目返回 409。入站是 `POST /connector/telegram/{bot}` 和 `POST /connector/lark/{bot}`，不走网页登录。Telegram 用请求头 `X-Telegram-Bot-Api-Secret-Token`，飞书用请求头 `X-Lark-Token` 或正文里的 `token`，和存好的密钥不一致就拒绝，收件箱不写。校验打开同一全局产品库，Bot 名只负责投递路由，不负责密钥分桶。对上的消息写成来源 `telegram` 或 `lark` 的不可信事件，正文是聊天 id 和文本，没有密钥。飞书的 `url_verification` 只回 `challenge`，不唤醒。同一条 `update_id` 或 `message_id` 只收一次。出站工具是 `telegram_send` 和 `lark_send`，装上后登记进注册表，经代理门调用，schema 不进 `tools[]`。调用先落一份草稿，确认卡给用户看收件人和正文；没点头就不发，草稿留着。点头之后才请求 Telegram 的 `sendMessage`，或飞书自定义机器人的 webhook。返回给模型的错误里，密钥换成 `[secret]`。卸下这条 Link 时删掉它的密钥。
- **市场条目**：标明类型（原生 Link 插件，或 MCP）、能力（工具 / 入站事件）、以及需要的密钥。
- **编码代理器官**：运行中改 Bot 名时，现 Record/Link 与任务队列保留，记录、卡片 transcript 和终态 Inbox 投递在当前路径短 IO 回调内完成；后端调用、进程等待和终态观察者在该锁外。原 Move 与记录文件锁串行短写，不等待整次任务执行；仅 Bot/work 内部前缀的 cwd/任务路径重基，外部自定义项目目录保留。后续 Shell/子进程使用当前实例身份，原 ID、队列准入和后端不因改名重启。和子代理分开。一个 Bot 可以同时留下多条编码任务，每条有自己的工作目录、仓库、步数上限和时间上限，不套用子代理的 16 步、10 分钟。记录在 `bots/<name>/code/<id>.json`，id 以 `ca_` 开头。同时只有一条是 `running`，再开始的进 `queued`。`code_start` 记录工作目录、目标和会改文件，然后启动；按权限表它是普通动作，不弹确认卡。Bot 可以补充（`code_steer`）、排队（`code_queue`）、打断（`code_interrupt`）、取消（`code_cancel`），并用 `code_show` 看记录。取消正在跑的那条时，队列里最早的一条变成 `running`。完成、失败或取消时向该 Bot 的收件箱投来源 `coding-agent` 的不可信事件。这些工具常驻注册表，经代理门调用。内核没有新的对象。后端三选一。`XBOT_CODE_AGENT` 是已有编码代理的可执行文件，优先用它。没设时在 PATH 里依次找 `cursor-agent`、`codex`、`claude`。`claude` 和 `cursor-agent` 加 `-p`，`codex` 加 `exec`，其它命令仍把目标当作唯一参数。子进程环境只有基础变量、这次任务的 `XBOT_CODE_*` 和当前实例 CLI 身份变量，不带供应商密钥。标准输出和标准错误按行追加进该 Bot 的 transcript，每条包在 `<coding_card id status>` 里。对话里同一个 id 只显示最新的一张卡片。进程结束时再追加一张终态卡片，状态是 done、failed 或 cancelled。取消之后记录已经不是 running，这张卡片仍然要写，不能停在 running。这些卡片不进模型上下文，也不进记忆抽取。`code_show` 在任务还在跑时能看到已经流出来的输出。`code_cancel` 停掉进程，并杀掉它所在的进程组，避免子进程把管道占住。没有外部命令时，`xbot chat --runner` 或 `XBOT_RUNNER_URL` 把任务交给 `xbot runner`。都没有时，用这个 Bot 绑定的模型在本进程里跑。步数和时间都用这条任务自己的上限。仓库非空且工作目录还没有 `.git` 时先克隆。这三个都没配时，仍然只写记录。


## 连接器发现与加载诊断

商店安装全局能力后，Agent读连接器摘要。MCP 经 `"$XBOT_BIN" mcp tools <server> --self --json` 发现、describe读完整原Spec、call用原名执行，不登记tool_index或模型tools[]；非MCP仍用links load与tools门。目录标题/id/mcp:来源标签保留用于安装/展示，不是旧工具执行兼容入口。

MCP 的 `LoadTools(ctx)` 返回工具或可读错误；Manager状态只缓存真实发现/连接结果，HTTP GET不额外探测。错误注明服务器和阶段（start、initialize、tools/list、connection），不把失败缓存成成功的空列表，合法空工具列表也明确报告未提供工具。stderr 保留最多 8 KiB，已声明的凭据按启动时值脱敏，超长输出裁掉末尾不完整行；错误输出也有 8 KiB 上限。stdio 在 stdout 读完后等待进程，保留 stderr 和退出码；initialize/list 整次发现保 15 秒，工具 HTTP POST 沿各自调用 context、不受通用 15 秒 cap，也不占 stdio 帧 gate。stdio 等 gate 可取消，完整帧写的零字节可恢复 deadline 取消保流；半帧/短写/硬失败先取消进程再 close/reap，返回 outcome_unknown 不重试。取消原 request ID 的提示异步、至多一次且 250ms 有界，不阻 caller 清理。启动/握手失败在当前实例保留；配置变更按既有机制换实例，或重启后重连。tools/list 的非断线失败可再次加载。

商店 API 增加 `load_id` 和按 Bot 列出的 MCP `runtime`（configured / ready / error、工具数、脱敏错误），仅查询已有实例，不主动探测或拉进程；配置不匹配的旧实例状态不复用。ready 只代表已取得非空工具表，不保证浏览器依赖或每个工具调用都成功。旧 `state=connected` 是安装/凭据状态，前端本次未改，尚不显示新的运行状态。接口见 [API](../API.md#连接应用的运行状态)。

## MCP CLI、只读与旧入口退役

主线、legacy子代理和continuable子代理都不再接收MCP schema，旧fallback/冷却/前缀路由已退。普通provider错误不因MCP额外重试；context overflow保原fit重试、预算校准与Descriptor实际路由。非MCP Tools门仍有memory/routine/context/peers/bots/links/secrets/shelljobs/agents/skills消费者。历史transcript保留可读，旧mcp_执行名不暗启adapter。替代范围见 [ADR 0047](../adr/0047-mcp-cli-domain-entry.md)。

Agent self以原source endpoint/ref为权威，XBOT_BOT仅诊断；human显式http+bot走本机owner cookie会话，未显式root不发送客户端默认Root。MCP client随ctx、默认timeout0、无proxy/redirect；profile原10s不影响MCP。research仅POSIX当前BIN或精确受控XBOT_BIN单直调，业务上只放self读取/readonly调用，不把通用shellWords当授权解析器；cmd/PowerShell和远端runner不冒称支持。完整HTTP/结果合同见 [API](../API.md#mcp-运行时-cli)。

## 坑
- 跑着独立用户的保险箱守护进程（`xbot vaultd`）时 → 本进程拿不到连接器 token 的明文，没法校验入站签名 → Telegram 和飞书的 webhook 入站返回 401 并记一行日志，不放行也不做假校验。要收入站消息，暂时只能用本地同用户的保险箱。出站发送不受影响。
- 工具的 JSON Schema 没有必填参数时 → Go 把 nil 切片编成 `"required": null`，DeepSeek 直接拒收整个请求 → `required` 一律写空数组 `[]`（[LESSONS](../../LESSONS.md)，`2ed8ca3`）。
- 共享入口（例如入站 hub）使用资源时，按产品定义确定作用域：保险库是整机全局，投递目录/工作目录仍按调用 Bot；不以「第一个 Bot」冒充全局。

设置商店安装在写配置前探测（[ADR 0031](../adr/0031-store-keys-in-settings.md)）：MCP 拉起并读取工具表，Playwright 另调一次 `browser_navigate`；Context7 另用密钥查询上游；Telegram 调 `getMe`；飞书向 webhook 发不存在的 `msg_type`，19001/19021/19022 判失败，其余视为 token 有效且不会投递。商店设置收密钥不经聊天，API 不返回密钥；历史配置的列表状态仍按配置与密钥存在判断，不代表重新探测。
