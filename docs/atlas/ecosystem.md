# 生态：Link、MCP、技能、连接器、编码代理

> **30 秒版**：外部能力都以 Link 接入：内置 Link、MCP 适配器、用户技能、Telegram/飞书连接器、编码代理。Bot 用 `links` 自己搜索、安装、加载。

## 边界
负责：各类 Link 的接入方式。不负责：确认规则（见 [安全](security.md)），各片进度（见 [MILESTONES](../MILESTONES.md)）。

## 怎么运转
- **按解释器执行命令**：工具目录不注册泛用 `shell`。macOS 探测 `zsh`、`bash`、`sh`，Linux 探测 `bash`、`sh`、`zsh`；Windows 探测 `powershell`（优先 pwsh）、`cmd`，以及 Git 安装目录中的 `git-bash`。只挂载能找到的可执行文件；版本探测每个最多 1 秒、输出最多 512 字节，失败仍挂载并标「版本未知」，发现结果进程内缓存。描述注明解释器名和版本；调用必须带 `description` 说明目的（最多 1024 字节），命令仍限 16 KiB，原始参数限 128 KiB。主线、子代理、编码执行和 runner 共用这套发现；评测沙箱明确使用 `sh`。各壳复用现有权限、机器开关、cwd、Jobs、输出脱敏和取消机制；任务记录保存实际工具名和用途。
- **原生内置 Link**：Shell 和文件（`read_file`、`write_file`、`edit_file` 受内核的文件新鲜度检查：没读过的已有文件不能改，读过之后被别人改了就拒绝写，见 [内核](kernel.md)）、浏览器（通过 CDP 驱动本机 Chrome，工具 `browser_open`、`browser_snapshot`、`browser_click`、`browser_stop`）、桌面操作、HTTP 请求（`http_request`）、公开网页（`web_fetch`、`web_search`）和看图（`view_image`）。内核挂上原任务表之后，所有工具共用慢调用生命周期，默认前台等 2 秒，插话立即让出；不取消实际运行，输出仍进 Bot 的 `shell-jobs/`，复用 `shell_output`、`shell_status`、`shell_cancel`，完成为普通 Inbox 回报。`timeout_seconds` 仅缩短 shell 的前台等待；未挂表的单独 shell 与评测沙箱仍沿原硬超时，详见 [内核](kernel.md)「慢工具后台化」。挂上会话之后，前台 `cd` 留在这个 Bot 上，结果带 `cwd:`；目录丢了或不在工作区里就回到工作区并写明。后台任务记下启动时的目录。文件工具和 `view_image` 的相对路径跟着调用方的目录走（前台、某个后台分支或某个子代理），绝对路径不变；解析符号链接之后必须还在工作区或共享目录里，沙箱里则钉在沙箱根上。`web_fetch` 只取公开的 http(s)，HTML 收成文字，重定向最多 5 次，超时 20 秒，正文超过约 48 KiB 截断；私网、回环、链路本地、元数据和 DNS 前后两次结果不一致都拒绝。`web_search` 默认使用 DuckDuckGo，无需密钥。全局网页搜索设置沿用 `web.json`：`search_enabled` 缺省为开，`search_mode` 缺省为 `auto`，`local` 表示强制本机；本机供应商仍在 `search.backend`。切换本机供应商只改选择，保留已有 DeepSeek 的密钥绑定和端点。设置页首次保存后以文件内选择为准，不再被旧的 `XBOT_SEARCH_*` 选择覆盖。`config.SearchProviders` 是九家名单的唯一来源；DuckDuckGo、DeepSeek 已实现，其余选择明确报不可用。DeepSeek 仍走官方 `POST /v1/tools/search`，不传模型。设置页校验沿用已配置的可信出口网段，仅向官方地址发送，成功后复用 `SaveEnvKey` 写入本机 `env`（0600、文件锁、原子替换），使用专属 `XBOT_SEARCH_DEEPSEEK_KEY`，不覆盖模型密钥；运行时直接读取专属条目，所以 `serve` 重启后也能使用，不依赖桌面入口加载环境。凭据读取、保存与脱敏登记共用同一文件锁，地址与密钥一次解析为一致快照。启动入口在任何工具可用前把全部已保存的搜索密钥加入现有持有及脱敏路径，包括未选中的供应商；密钥不回传前端。旧显式 `api_key_env` 与安全地址限制仍可用；使用设置页校验后的密钥一律发往官方地址。内核挂载一次动态搜索对象，调用时读取选择，已有 Bot 不需重启。DuckDuckGo 返回非 200 或挑战页时直接报错，让模型告诉主人，不说明怎么换后端。两者的结果都包在 `<untrusted_event>` 里。结束标签换成 `[/untrusted_event]`，不再留下还能被认成标签的形式；大小写、空白、全角、全角下划线、小写小于号、分数斜线、零宽字符、组合附加符号、形近括号（`‹›`、`〈〉`、`⟨⟩`、`«»`、`˂˃` 等，和记忆围栏用同一份）、数学和带圈字母这类兼容字形、形近的西里尔和希腊字母，以及 `&lt;/untrusted_event&gt;` 都会拆开。超长工具结果仍走 transcript 的 blob 和预览。`view_image` 接受 JPEG、PNG、GIF、WebP，文件超过 32 MiB 不读，超过 10 MiB 不送给模型，边长超过 2048 会缩小（WebP 超了就拒绝，读不出宽高也拒绝）。边长不超过 2048 的 JPEG、PNG、GIF 原样通过，不按解码后的字节数拒绝。要缩小的那一路才解码，一次解码最多按 160 MiB 估计（渐进式 JPEG 按每像素 12 字节，16 位彩色 PNG 按 8 字节，边长仍不超过 4096），解码一次只跑一张；WebP 不解码，不占这份额。模型看不看图写在模型条目的 `vision` 上：`deepseek-flash`（以及名字里同时有 deepseek 和 flash 的）默认能看，`deepseek-chat` 和 `deepseek-v4-pro` 默认不能；显式 `vision: true/false` 盖过默认。没绑定供应商时跟 `XBOT_MODEL`，不再写死 deepseek-flash。不能看的模型直接得到 `model <id> does not support vision`，不把图片悄悄丢掉。能看的模型在这一轮里收到 Chat Completions 的 `image_url` 数据 URL，只保留最新一批，仍是一轮最多 4 张、合计 10 MiB。图片字节不进 transcript，这一轮结束才从内存里清掉，下一轮没有。子代理连续调用工具时也只留最新一批，在没有工具调用的回复之后全部清掉，再接排队或插话。
- **MCP 适配器**：内置的 Link。服务器登记在主人全局的根目录 `mcp.json`（所有 Bot 共用），Bot 自己目录里的 `mcp.json` 仍会读，同名时 Bot 的那条覆盖全局；字段是名字、命令、参数，以及密钥环境变量的名字。密钥的值不写进文件，也不进接口。拉起进程时不用 shell，环境只留一小份基础变量（`PATH`、`HOME`、`TMPDIR`、`LANG`、`SYSTEMROOT`），再加上这些名字的值：先查这个 Bot 的 `secrets.json`（拉起时现读，`links install` 填的值在这里），没有再用当前进程环境里的值。HTTP 把同名且已设置的非供应商密钥放进请求头。供应商 API key（`HoldKeys` 记下的名字，含 `XBOT_API_KEY` 和各 provider 的 `api_key_env`）不能写入 `secret_envs`，不进子进程环境，也不进 HTTP 头，并且不从内存里的 key 副本读出。传输有两种，协议版本都是 `2024-11-05`。stdio 是按行分隔的 JSON-RPC，拉起进程时不用 shell。Streamable HTTP 把 `url` 记在同一份 `mcp.json`：有地址就不再用命令。客户端 POST 一条 JSON-RPC，`Accept` 同时写 `application/json` 和 `text/event-stream`。JSON 响应压成一行再交给原来的读循环；SSE 只取 `data`。响应头 `Mcp-Session-Id` 之后每次都带上。`202` 空响应是通知，不当成失败。拿到会话之后对同一地址 GET 一条 SSE，用来收服务器主动发的通知；对方返回 405 就当没有这条流。两种都是先 `initialize`，再 `notifications/initialized`，然后 `tools/list`（跟着 `nextCursor`，最多 20 页）。模型调用走 `tools/call`。工具名是 `mcp_<服务器>_<工具>`，压到 64 个字符以内。`readOnlyHint` 为真的调用不用确认，其余要确认。`isError` 当成工具失败。图片内容丢掉，文本拼起来。入站是可选的：`notifications/xbot/event` 和 `notifications/message` 的 `text` 写成来源 `mcp:<名字>` 的不可信事件；没有这类通知也可以。通知通道满了就丢掉，不能堵住工具调用。目录里的 `mcp` 条目仍然不能一键安装，因为一条授权没有命令可跑。另有一份打进二进制的连接器目录（JSON），不是托管市场。商店「已添加/已连接」必须表示鉴权后续已完成：目录声明了密钥就走确认卡，声明了 OAuth 就走浏览器登录；未完成不得标已装（见 [ADR 0023](../adr/0023-connector-auth-followthrough.md)）。「一键」只省 CLI，不省凭证。`xbot connector list` 列出 id、传输、命令或地址、密钥名。`xbot connector add <bot> <id>` 把这一条抄进该 Bot 的 `mcp.json`，只启用这一个 Bot（重复添加不报错）；设置里的应用商店则写进全局 `mcp.json`，原生的电脑操作、浏览器写进根目录 `apps.json`，所有 Bot 下一轮都有。系统提示里单独一块「连接器」，每行 `名称:描述`，用法靠 `links load`（名称或 id 都认）渐进展开，不放 MCP 的工具定义。`xbot connector remove <bot> <id>` 删掉。目录里没有密钥的值。`chat` 和 `serve` 都会把这些事件推进收件箱。`serve` 每一轮用来处理收件箱的内核是短命的，不在那上面再挂一条连接；第一次有服务器时另留一个长期内核来收通知。这一轮已经接上之后再改 `mcp.json`，要重新打开 `chat` 或重启 `serve`。
- **Bot 自己管理 Link**：内置工具 `links`，动作是 `search`、`install`、`remove`、`load`。`search` 查精选目录，中文摘要之外也匹配英文关键词和 id，返回 id、一行摘要和密钥的名字。`install` 每次都走主人的确认卡，和 shell 这类需要确认的工具同一条审批。这条 Link 如果声明了密钥，确认卡带上密钥的名字，主人在界面里填写值。连接器（Telegram、飞书）的 token 写进该 Bot 的保险箱，其余 Link 的密钥写进该 Bot 的 `secrets.json`（权限 0600）；两种都不进确认摘要，不进工具结果，也不进给模型的提示。没填齐就不安装。商店里以连接器目录运行的应用（如 Context7）也走这条：`id` 认目录 id、商店标题或 `mcp:<id>`，确认卡列出目录的 `secret_envs`，填齐后值写进该 Bot 的 `secrets.json`，再把这一行写进全局 `mcp.json`；全局里已有缺这些密钥名的旧条目时换成目录这一行。`remove` 删掉全局和该 Bot 的条目及该 Bot 存的密钥；商店「移除」同时删掉主人各 Bot 存的这些密钥。`search` 列出这些行，条目带齐密钥名、且每个密钥在这个 Bot 的 `secrets.json` 或进程环境里有非空值才算 installed；商店列表逐个 Bot 按拉起时的同一取法判断（先该 Bot 的 `secrets.json`，那里没有值才看进程环境；存了空白就是空白，不回落环境），任一 Bot 每个密钥都非空才算已连接，只有名字不算。还没有运行时的条目，即使主人填了密钥，也不安装、不把值落盘。`remove` 也要主人确认，确认后同时删掉这条 Link 的密钥：保险箱里的用 `backend.Remove` 删，其余从 `secrets.json` 删。系统提示的「连接器」块只列商店类应用与自定义 MCP，每行 `名称:描述`，不放工具 schema；webhook/watch/skills/coding-agent 不在这个块，原有加载与独立技能摘要不变。这一段大约 1KB；超了就只列 id，摘要用 `search` 查。`load` 把该 Link 的工具 schema 加进这一轮后面的模型调用，下一轮丢掉。`install` 写上授权之后，这条 Link 立刻挂到当前进程，不用重启 `serve`，同一次对话里 `load` 就能列出工具。终端的 `--yes` 不能代替主人填写密钥。
- **用户技能**：还是已有的 `skills` Link，不另起机制。每个数据根一份本机技能库，路径是该数据根下的 `skills/<slug>/SKILL.md`。格式和 `~/.agents/skills` 一样：YAML 头里 `name` 是 slug，可选 `title` 是人读短名（如「记一下」），`description` 是说明，后面是 markdown；旧文件的可读 name 继续作为无 title 时的降级。`xbot skill import <path>` 把技能拷进本机技能库；源路径可以是符号链接。库里的目录如果本身是指向技能目录的符号链接，同样能列出来、能读。有技能授权的本机 Bot 都能看见这份库，包括无 owner 和多 owner 的 Bot。每个 Bot 用自己的停用名单关掉其中几条，不影响其他 Bot。聊天群不是 Bot，没有技能库。系统提示的 Skills 段写出运行时技能库目录，每条技能一行（技能 id 和 description），并写明调用 `read_skill`、把该行的 id 传进去，以及用户技能盖过这个 Bot 的默认习惯。这一段大约 1KB；超了就只留名字和怎么读。正文不进提示。只要提示里列了至少一条技能，`read_skill` 就在工具列表里，不用先 `links load`。`write_skill` 仍要 `load`。`read_skill` 和 `write_skill` 的工具描述也使用运行时技能库目录。Bot 用 `read_skill` 的 `id` 参数读全文，不靠在磁盘上查找。全文只留在当前这一轮，下一轮不在 transcript 里。主线在已授权 skills 且本轮 load 后可直接用 `write_skill` 创建或覆盖本机技能库中的技能，Dispatch 开着也不隐藏它；权限复用 `review.Normal`，不弹确认卡。catalog 和 grant 文案均指向本机技能库。`write_skill` 的可选 `title` 单行化并安全引用后写入 frontmatter；可选 `scope=self` 只启用当前 Bot，具体 Bot 名在本数据根的本机 Bot 中忽略大小写匹配，未知或歧义目标在落盘前拒绝。省略/空 scope 全开；服务端只处理显式字段，不扫描 transcript。同一库的 `write_skill` 文件与默认范围更新以文件锁串行；写入当次沿用 `EnableSkill` / `DisableSkill` 设置默认，之后主人手动开关仍有效。 设置页「技能」走库级接口列出和导入，导入由浏览器读出文件夹里的 SKILL.md 发来，同名要确认才覆盖，检查加写入在同一把锁里；开关仍是各 Bot 的 `disabled_skills`。见 [界面](ui.md#技能设置)。
- **旧技能迁移**：CLI 技能入口、内核打开和网页注册时按当前数据根迁移，`~/.xbot` 与 `~/.xbot-dev` 分别处理。一级已有 `SKILL.md` 不作 owner 扫描；旧 `owner/slug` 整目录提升，保留辅助文件。冲突比较 `SKILL.md` mtime，较新者保留原 slug（同时间优先已扁平版本），其余为 `<slug>__from_<owner>`；原有扁平版本旁路时来源为 `local`，旁路重名加 `__2` 等后缀，不覆盖。操作路径追加至 `skills/.migration.log`，失败条目保留重试，其余继续；迁移和导入、`write_skill` 共用 `skills/.write.lock`。已完成的迁移重跑不新增备份或日志。
- **Link 插件市场**：上架的是实现 Link 协议的插件（出站工具 + 入站 Event），不是 MCP 市场。自定义聊天室、Telegram、飞书（Lark）这类连接器都可以上架，把外面收到的消息推进来，变成 Event。一份精选清单，默认不安装，点一下就添加。
- **连接器**：Telegram 和飞书。装上之后，外面的消息才进收件箱。安装要主人在确认卡里填密钥（`TELEGRAM_BOT_TOKEN`、`LARK_APP_SECRET`）。值存进该 Bot 的保险箱（`vault.Backend`），名字是 `telegram.token`、`lark.token`，分别只绑定 `api.telegram.org` 和 `open.feishu.cn`；不进系统提示，不进 transcript，也不进工具结果。出站请求只带 `{{secret:telegram.token}}` 这类占位符，真值由保险箱的出站代理在请求离开进程时填进去（见 [安全](security.md)）。旧版本留在 `secrets.json` 里的明文，在连接器第一次被挂上时迁进保险箱，全部写入成功后删掉明文；中途失败就保留明文，下次启动再迁，重复执行没有副作用。命令行安装从同名环境变量读；变量是空的就不装、不落盘。网页 `POST /api/bots/{name}/links` 不接收密钥，声明了密钥的条目返回 409。入站是 `POST /connector/telegram/{bot}` 和 `POST /connector/lark/{bot}`，不走网页登录。Telegram 用请求头 `X-Telegram-Bot-Api-Secret-Token`，飞书用请求头 `X-Lark-Token` 或正文里的 `token`，和存好的密钥不一致就拒绝，收件箱不写。校验按请求里的 Bot 打开它自己的保险箱，不共用某一个 Bot 的。对上的消息写成来源 `telegram` 或 `lark` 的不可信事件，正文是聊天 id 和文本，没有密钥。飞书的 `url_verification` 只回 `challenge`，不唤醒。同一条 `update_id` 或 `message_id` 只收一次。出站工具是 `telegram_send` 和 `lark_send`。schema 不在首轮工具里，`links load` 之后只留在当前这一轮。调用先落一份草稿，确认卡给主人看收件人和正文；没点头就不发，草稿留着。点头之后才请求 Telegram 的 `sendMessage`，或飞书自定义机器人的 webhook。返回给模型的错误里，密钥换成 `[secret]`。卸下这条 Link 时删掉它的密钥。
- **市场条目**：标明类型（原生 Link 插件，或 MCP）、能力（工具 / 入站事件）、以及需要的密钥。
- **编码代理 Link**：和子代理分开。一个 Bot 可以同时留下多条编码任务，每条有自己的工作目录、仓库、步数上限和时间上限，不套用子代理的 16 步、10 分钟。记录在 `bots/<name>/code/<id>.json`，id 以 `ca_` 开头。同时只有一条是 `running`，再开始的进 `queued`。`code_start` 记录工作目录、目标和会改文件，然后启动；按权限表它是普通动作，不弹确认卡。Bot 可以补充（`code_steer`）、排队（`code_queue`）、打断（`code_interrupt`）、取消（`code_cancel`），并用 `code_show` 看记录。取消正在跑的那条时，队列里最早的一条变成 `running`。完成、失败或取消时向该 Bot 的收件箱投来源 `coding-agent` 的不可信事件。这些工具的 schema 要 `links load coding-agent` 之后才进当前这一轮。内核没有新的对象。后端三选一。`XBOT_CODE_AGENT` 是已有编码代理的可执行文件，优先用它。没设时在 PATH 里依次找 `cursor-agent`、`codex`、`claude`。`claude` 和 `cursor-agent` 加 `-p`，`codex` 加 `exec`，其它命令仍把目标当作唯一参数。子进程环境只有基础变量和这次任务的 `XBOT_CODE_*`，不带供应商密钥。标准输出和标准错误按行追加进该 Bot 的 transcript，每条包在 `<coding_card id status>` 里。对话里同一个 id 只显示最新的一张卡片。进程结束时再追加一张终态卡片，状态是 done、failed 或 cancelled。取消之后记录已经不是 running，这张卡片仍然要写，不能停在 running。这些卡片不进模型上下文，也不进记忆抽取。`code_show` 在任务还在跑时能看到已经流出来的输出。`code_cancel` 停掉进程，并杀掉它所在的进程组，避免子进程把管道占住。没有外部命令时，`xbot chat --runner` 或 `XBOT_RUNNER_URL` 把任务交给 `xbot runner`。都没有时，用这个 Bot 绑定的模型在本进程里跑。步数和时间都用这条任务自己的上限。仓库非空且工作目录还没有 `.git` 时先克隆。这三个都没配时，仍然只写记录。

## 连接器发现与加载诊断

商店安装全局能力后，Agent 先读「连接器」摘要，再用 `links` 的 `action=load`、`id=名称或 id` 加载。`ResolveApp` 统一解析商店标题、id 和 MCP 前缀，例如 `电脑操作` / `desktop`、`浏览器` / `browser`、`Playwright` / `playwright` / `mcp:playwright`。原生电脑、CDP 浏览器和精选 MCP 共用加载入口，各自实现不合并。只有本轮 load 成功才把 MCP 工具加入后续模型请求，下一轮清除展开态。

MCP 的 `LoadTools(ctx)` 返回工具或可读错误；兼容 Link 的 `Tools()` 失败时，原因保留在 `Status()`。错误注明服务器和阶段（start、initialize、tools/list、connection），不把失败缓存成成功的空列表，合法空工具列表也明确报告未提供工具。stderr 保留最多 8 KiB，已声明的凭据按启动时值脱敏，超长输出裁掉末尾不完整行；错误输出也有 8 KiB 上限。stdio 在 stdout 读完后等待进程，保留 stderr 和退出码；HTTP 请求沿调用 context 取消，单次 RPC 沿用 15 秒上限。启动/握手失败在当前实例保留；配置变更按既有机制换实例，或重启后重连。tools/list 的非断线失败可再次加载。

商店 API 增加 `load_id` 和按 Bot 列出的 MCP `runtime`（configured / ready / error、工具数、脱敏错误），仅查询已有实例，不主动探测或拉进程；配置不匹配的旧实例状态不复用。ready 只代表已取得非空工具表，不保证浏览器依赖或每个工具调用都成功。旧 `state=connected` 是安装/凭据状态，前端本次未改，尚不显示新的运行状态。接口见 [API](../API.md#连接应用的运行状态)。

## MCP schema 降级

主对话与本机子代理只对明确的 HTTP 400 工具 schema 错误降级，保留 overflow 原有切短重试，鉴权失败与普通 400 原样返回。错误点名当前请求的 MCP 工具时只摘掉它；没有名字时临时摘掉该请求全部 MCP 工具，不动内置工具。请求尾部追加可读说明（最多列 32 个名称），不复制上游错误正文、不改原 schema 或权限；原 `trace.jsonl` 记 `mcp_schema / tools_suspended`。同一次模型调用最多增加一次 schema 重试，已经流出文字或已取消时不重试；再次失败仍返回错误。

进程内冷却缓存按 Bot 路径、绑定模型、工具名与 schema 哈希隔离，只存哈希和到期时间，最多 4096 条，满时淘汰最早到期项；短命内核与后续轮次复用。30 分钟后、schema 或绑定模型变化、进程重启后可重新尝试原定义。无法定位工具时可能暂时连同健康 MCP 工具一起停用；冷却期间重复 `links load` 不解除停用。待验收设计见 [MCP schema 被拒时降级](../dev/mcp-schema-fallback.md)。

## 坑
- 跑着独立用户的保险箱守护进程（`xbot vaultd`）时 → 本进程拿不到连接器 token 的明文，没法校验入站签名 → Telegram 和飞书的 webhook 入站返回 401 并记一行日志，不放行也不做假校验。要收入站消息，暂时只能用本地同用户的保险箱。出站发送不受影响。
- 工具的 JSON Schema 没有必填参数时 → Go 把 nil 切片编成 `"required": null`，DeepSeek 直接拒收整个请求 → `required` 一律写空数组 `[]`（[LESSONS](../../LESSONS.md)，`2ed8ca3`）。
- 共享入口（例如入站 hub）要用某个 Bot 的资源时 → 取「第一个 Bot」的保险箱或目录会拿错人 → 按这次请求的 Bot 去打开。
