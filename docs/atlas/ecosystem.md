# 生态：Link、MCP、技能、连接器、编码代理

> **30 秒版**：外部能力都以 Link 接入：内置 Link、MCP 适配器、用户技能、Telegram/飞书连接器、编码代理。Bot 用 `links` 自己搜索、安装、加载。

## 边界
负责：各类 Link 的接入方式。不负责：确认规则（见 [安全](security.md)），各片进度（见 [MILESTONES](../MILESTONES.md)）。

## 怎么运转
- **原生内置 Link**：Shell 和文件（`read_file`、`write_file`、`edit_file` 受内核的文件新鲜度检查：没读过的已有文件不能改，读过之后被别人改了就拒绝写，见 [内核](kernel.md)）、浏览器（通过 CDP 驱动本机 Chrome，工具 `browser_open`、`browser_snapshot`、`browser_click`、`browser_stop`）、桌面操作、HTTP 请求（`http_request`）、公开网页（`web_fetch`、`web_search`）和看图（`view_image`）。内核挂上任务表之后，`shell` 默认 120 秒、最长 600 秒，到点不杀，输出进该 Bot 的 `shell-jobs/`，用 `shell_output`、`shell_status`、`shell_cancel` 看和停。挂上会话之后，前台 `cd` 留在这个 Bot 上，结果带 `cwd:`；目录丢了或不在工作区里就回到工作区并写明。后台任务记下启动时的目录。文件工具和 `view_image` 的相对路径跟着调用方的目录走（前台、某个后台分支或某个子代理），绝对路径不变；解析符号链接之后必须还在工作区或共享目录里，沙箱里则钉在沙箱根上。`web_fetch` 只取公开的 http(s)，HTML 收成文字，重定向最多 5 次，超时 20 秒，正文超过约 48 KiB 截断；私网、回环、链路本地、元数据和 DNS 前后两次结果不一致都拒绝。`web_search` 的代码默认仍是 DuckDuckGo 的 HTML 接口，不需要密钥。部署要换成 DeepSeek 时，在 `~/.xbot/web.json` 写 `{"search":{"backend":"deepseek","base_url":"https://api.deepseek.com"}}`，或设 `XBOT_SEARCH_BACKEND=deepseek`。请求是官方 Search API 的 `POST /v1/tools/search`，正文只有 `query` 和 `count`，不传模型、不走 Responses API。没写 `api_key_env` 时只用 `DEEPSEEK_API_KEY`，不回落到 `XBOT_API_KEY`。现场如果只有 `XBOT_API_KEY`（一份 DeepSeek 密钥），要显式写 `{"search":{"backend":"deepseek","api_key_env":"XBOT_API_KEY"}}` 才复用它。供应商密钥（`DEEPSEEK_API_KEY`、`XBOT_API_KEY`，或 `providers.json` 里的 `api_key_env`）只能发往 `https://api.deepseek.com`；`providers.json` 读失败时同样拒绝发往别的主机。已经收进内存、但不在这份名单里的搜索密钥仍可以走别的 https 主机，`http` 一律拒绝。密钥不进日志。DuckDuckGo 返回非 200 或挑战页时直接报错，让模型告诉主人，不说明怎么换后端。两者的结果都包在 `<untrusted_event>` 里。结束标签换成 `[/untrusted_event]`，不再留下还能被认成标签的形式；大小写、空白、全角、全角下划线、小写小于号、分数斜线、零宽字符和 `&lt;/untrusted_event&gt;` 都会拆开。超长工具结果仍走 transcript 的 blob 和预览。`view_image` 接受 JPEG、PNG、GIF、WebP，文件超过 32 MiB 不读，超过 10 MiB 不送给模型，边长超过 2048 会缩小（WebP 超了就拒绝，读不出宽高也拒绝）。边长不超过 2048 的 JPEG、PNG、GIF 原样通过，不按解码后的字节数拒绝。要缩小的那一路才解码，一次解码最多按 160 MiB 估计（渐进式 JPEG 按每像素 12 字节，16 位彩色 PNG 按 8 字节，边长仍不超过 4096），解码一次只跑一张；WebP 不解码，不占这份额。模型看不看图写在模型条目的 `vision` 上：`deepseek-flash`（以及名字里同时有 deepseek 和 flash 的）默认能看，`deepseek-chat` 和 `deepseek-v4-pro` 默认不能；显式 `vision: true/false` 盖过默认。没绑定供应商时跟 `XBOT_MODEL`，不再写死 deepseek-flash。不能看的模型直接得到 `model <id> does not support vision`，不把图片悄悄丢掉。能看的模型在这一轮里收到 Chat Completions 的 `image_url` 数据 URL，只保留最新一批，仍是一轮最多 4 张、合计 10 MiB。图片字节不进 transcript，这一轮结束才从内存里清掉，下一轮没有。子代理连续调用工具时也只留最新一批，在没有工具调用的回复之后全部清掉，再接排队或插话。
- **MCP 适配器**：内置的 Link。每个 Bot 在自己的 `mcp.json` 里登记服务器，字段是名字、命令、参数，以及密钥环境变量的名字。密钥的值不写进文件，也不进接口。拉起进程时不用 shell，环境只留一小份基础变量（`PATH`、`HOME`、`TMPDIR`、`LANG`、`SYSTEMROOT`），再加上这些名字在当前进程环境里已经有的值。HTTP 把同名且已设置的非供应商密钥放进请求头。供应商 API key（`HoldKeys` 记下的名字，含 `XBOT_API_KEY` 和各 provider 的 `api_key_env`）不能写入 `secret_envs`，不进子进程环境，也不进 HTTP 头，并且不从内存里的 key 副本读出。传输有两种，协议版本都是 `2024-11-05`。stdio 是按行分隔的 JSON-RPC，拉起进程时不用 shell。Streamable HTTP 把 `url` 记在同一份 `mcp.json`：有地址就不再用命令。客户端 POST 一条 JSON-RPC，`Accept` 同时写 `application/json` 和 `text/event-stream`。JSON 响应压成一行再交给原来的读循环；SSE 只取 `data`。响应头 `Mcp-Session-Id` 之后每次都带上。`202` 空响应是通知，不当成失败。拿到会话之后对同一地址 GET 一条 SSE，用来收服务器主动发的通知；对方返回 405 就当没有这条流。两种都是先 `initialize`，再 `notifications/initialized`，然后 `tools/list`（跟着 `nextCursor`，最多 20 页）。模型调用走 `tools/call`。工具名是 `mcp_<服务器>_<工具>`，压到 64 个字符以内。`readOnlyHint` 为真的调用不用确认，其余要确认。`isError` 当成工具失败。图片内容丢掉，文本拼起来。入站是可选的：`notifications/xbot/event` 和 `notifications/message` 的 `text` 写成来源 `mcp:<名字>` 的不可信事件；没有这类通知也可以。通知通道满了就丢掉，不能堵住工具调用。目录里的 `mcp` 条目仍然不能一键安装，因为一条授权没有命令可跑。另有一份打进二进制的连接器目录（JSON），不是托管市场。`xbot connector list` 列出 id、传输、命令或地址、密钥名。`xbot connector add <bot> <id>` 把这一条抄进该 Bot 的 `mcp.json`，只启用这一个 Bot。`xbot connector remove <bot> <id>` 删掉。目录里没有密钥的值。`chat` 和 `serve` 都会把这些事件推进收件箱。`serve` 每一轮用来处理收件箱的内核是短命的，不在那上面再挂一条连接；第一次有服务器时另留一个长期内核来收通知。这一轮已经接上之后再改 `mcp.json`，要重新打开 `chat` 或重启 `serve`。
- **Bot 自己管理 Link**：内置工具 `links`，动作是 `search`、`install`、`remove`、`load`。`search` 查精选目录，中文摘要之外也匹配英文关键词和 id，返回 id、一行摘要和密钥的名字。`install` 每次都走主人的确认卡，和 shell 这类需要确认的工具同一条审批。这条 Link 如果声明了密钥，确认卡带上密钥的名字，主人在界面里填写值。连接器（Telegram、飞书）的 token 写进该 Bot 的保险箱，其余 Link 的密钥写进该 Bot 的 `secrets.json`（权限 0600）；两种都不进确认摘要，不进工具结果，也不进给模型的提示。没填齐就不安装。还没有运行时的条目，即使主人填了密钥，也不安装、不把值落盘。`remove` 也要主人确认，确认后同时删掉这条 Link 的密钥：保险箱里的用 `backend.Remove` 删，其余从 `secrets.json` 删。已安装的目录 Link 和 `mcp:<名字>` 在系统提示里各自只占一行（id 加一行摘要），不放工具 schema。这一段大约 1KB；超了就只列 id，摘要用 `search` 查。`load` 把该 Link 的工具 schema 加进这一轮后面的模型调用，下一轮丢掉。`install` 写上授权之后，这条 Link 立刻挂到当前进程，不用重启 `serve`，同一次对话里 `load` 就能列出工具。终端的 `--yes` 不能代替主人填写密钥。
- **用户技能**：还是已有的 `skills` Link，不另起机制。每个 owner 一份库，路径是 `~/.xbot/skills/<owner>/<slug>/SKILL.md`。格式和 `~/.agents/skills` 一样：YAML 头里有 `name` 和 `description`，后面是 markdown。`xbot skill import <path>` 把技能拷进这个 owner 的库；源路径可以是符号链接。库里的目录如果本身是指向技能目录的符号链接，同样能列出来、能读。恰好有一个 owner 的 Bot 默认看见这个人的全部技能。这个 Bot 可以用一份停用名单关掉其中几条，不影响同一个 owner 的其他 Bot。没有 owner 的 Bot、有多个 owner 的共用 Bot、以及别的 owner 的 Bot，都看不见这库。聊天群不是 Bot，没有技能库。系统提示里每条技能一行（技能 id 和 description），并写明调用 `read_skill`、把该行的 id 传进去，以及用户技能盖过这个 Bot 的默认习惯。这一段大约 1KB；超了就只留名字和怎么读。正文不进提示。只要提示里列了至少一条技能，`read_skill` 就在工具列表里，不用先 `links load`。`write_skill` 仍要 `load`。Bot 用 `read_skill` 的 `id` 参数读全文，不靠在磁盘上查找。全文只留在当前这一轮，下一轮不在 transcript 里。Bot 可以起草一条新技能或一份修改，`write_skill` 在写盘前走主人的确认卡，和别的需要确认的工具同一条审批。没点头就不写文件。
- **Link 插件市场**：上架的是实现 Link 协议的插件（出站工具 + 入站 Event），不是 MCP 市场。自定义聊天室、Telegram、飞书（Lark）这类连接器都可以上架，把外面收到的消息推进来，变成 Event。一份精选清单，默认不安装，点一下就添加。
- **连接器**：Telegram 和飞书。装上之后，外面的消息才进收件箱。安装要主人在确认卡里填密钥（`TELEGRAM_BOT_TOKEN`、`LARK_APP_SECRET`）。值存进该 Bot 的保险箱（`vault.Backend`），名字是 `telegram.token`、`lark.token`，分别只绑定 `api.telegram.org` 和 `open.feishu.cn`；不进系统提示，不进 transcript，也不进工具结果。出站请求只带 `{{secret:telegram.token}}` 这类占位符，真值由保险箱的出站代理在请求离开进程时填进去（见 [安全](security.md)）。旧版本留在 `secrets.json` 里的明文，在连接器第一次被挂上时迁进保险箱，全部写入成功后删掉明文；中途失败就保留明文，下次启动再迁，重复执行没有副作用。命令行安装从同名环境变量读；变量是空的就不装、不落盘。网页 `POST /api/bots/{name}/links` 不接收密钥，声明了密钥的条目返回 409。入站是 `POST /connector/telegram/{bot}` 和 `POST /connector/lark/{bot}`，不走网页登录。Telegram 用请求头 `X-Telegram-Bot-Api-Secret-Token`，飞书用请求头 `X-Lark-Token` 或正文里的 `token`，和存好的密钥不一致就拒绝，收件箱不写。校验按请求里的 Bot 打开它自己的保险箱，不共用某一个 Bot 的。对上的消息写成来源 `telegram` 或 `lark` 的不可信事件，正文是聊天 id 和文本，没有密钥。飞书的 `url_verification` 只回 `challenge`，不唤醒。同一条 `update_id` 或 `message_id` 只收一次。出站工具是 `telegram_send` 和 `lark_send`。schema 不在首轮工具里，`links load` 之后只留在当前这一轮。调用先落一份草稿，确认卡给主人看收件人和正文；没点头就不发，草稿留着。点头之后才请求 Telegram 的 `sendMessage`，或飞书自定义机器人的 webhook。返回给模型的错误里，密钥换成 `[secret]`。卸下这条 Link 时删掉它的密钥。
- **市场条目**：标明类型（原生 Link 插件，或 MCP）、能力（工具 / 入站事件）、以及需要的密钥。
- **编码代理 Link**：和子代理分开。一个 Bot 可以同时留下多条编码任务，每条有自己的工作目录、仓库、步数上限和时间上限，不套用子代理的 16 步、10 分钟。记录在 `bots/<name>/code/<id>.json`，id 以 `ca_` 开头。同时只有一条是 `running`，再开始的进 `queued`。`code_start` 记录工作目录、目标和会改文件，然后启动；按权限表它是普通动作，不弹确认卡。Bot 可以补充（`code_steer`）、排队（`code_queue`）、打断（`code_interrupt`）、取消（`code_cancel`），并用 `code_show` 看记录。取消正在跑的那条时，队列里最早的一条变成 `running`。完成、失败或取消时向该 Bot 的收件箱投来源 `coding-agent` 的不可信事件。这些工具的 schema 要 `links load coding-agent` 之后才进当前这一轮。内核没有新的对象。后端三选一。`XBOT_CODE_AGENT` 是已有编码代理的可执行文件，优先用它。没设时在 PATH 里依次找 `cursor-agent`、`codex`、`claude`。`claude` 和 `cursor-agent` 加 `-p`，`codex` 加 `exec`，其它命令仍把目标当作唯一参数。子进程环境只有基础变量和这次任务的 `XBOT_CODE_*`，不带供应商密钥。标准输出和标准错误按行追加进该 Bot 的 transcript，每条包在 `<coding_card id status>` 里。对话里同一个 id 只显示最新的一张卡片。进程结束时再追加一张终态卡片，状态是 done、failed 或 cancelled。取消之后记录已经不是 running，这张卡片仍然要写，不能停在 running。这些卡片不进模型上下文，也不进记忆抽取。`code_show` 在任务还在跑时能看到已经流出来的输出。`code_cancel` 停掉进程，并杀掉它所在的进程组，避免子进程把管道占住。没有外部命令时，`xbot chat --runner` 或 `XBOT_RUNNER_URL` 把任务交给 `xbot runner`。都没有时，用这个 Bot 绑定的模型在本进程里跑。步数和时间都用这条任务自己的上限。仓库非空且工作目录还没有 `.git` 时先克隆。这三个都没配时，仍然只写记录。

## 坑
- 跑着独立用户的保险箱守护进程（`xbot vaultd`）时 → 本进程拿不到连接器 token 的明文，没法校验入站签名 → Telegram 和飞书的 webhook 入站返回 401 并记一行日志，不放行也不做假校验。要收入站消息，暂时只能用本地同用户的保险箱。出站发送不受影响。
- 工具的 JSON Schema 没有必填参数时 → Go 把 nil 切片编成 `"required": null`，DeepSeek 直接拒收整个请求 → `required` 一律写空数组 `[]`（[LESSONS](../../LESSONS.md)，`2ed8ca3`）。
- 共享入口（例如入站 hub）要用某个 Bot 的资源时 → 取「第一个 Bot」的保险箱或目录会拿错人 → 按这次请求的 Bot 去打开。
