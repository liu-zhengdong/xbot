# 上下文与 transcript

> **30 秒版**：每个 Bot 一份只追加、带编号的 transcript；固定前缀保证缓存命中，压缩生成摘要块，原文永远保留并可检索、导出。

## 边界
负责：组装上下文、transcript 分段存储和索引、压缩、找回、导出、引用回复。不负责：分叉的分支规则（见 [插话时分叉](fork.md)）。

## 怎么运转
- **固定前缀**：人设、内核规则、Link 说明，在多次唤醒之间逐字节不变，保证模型服务商的前缀缓存能命中；工具按名字排序。提醒不进前缀，也不改 transcript 正文：按序号另存，组装时只贴在当时那一条的末尾，重放字节不变。
- **同一轮的工具调用并行**。一次模型回复里的多个工具调用同时执行，并尊重取消。需要主人确认的，一次只问一个，其余调用继续跑。结果按原来的调用顺序写回对话，历史和前缀缓存保持确定。同时写同一处由模型自己避开，内核不为此加特殊规则。
- **环境快照**：时间、可用工具、当前发送者、未读通知、常驻记忆等。每次唤醒和上一次对比，有变化才追加一条只写差异的环境更新，从不改写历史。小时仍按粗粒度更新。主人的本地时间精确到分钟，写成 `now: <RFC3339> (<时区>)`，只出现在环境更新里，不进固定前缀。
- **原始记录只追加**，每条消息有编号。压缩生成"摘要块"，记录覆盖的编号范围，可以层层合并。
- **分段存放**：一个 Bot 的原文按大约 8MB，或按 UTC 日期，滚成一段。文件名带这一段的序号范围。只有尾段可写，封存的段只读。旧的单文件 `transcript.jsonl` 在第一次打开时迁进分段；写好 `READY` 之后，原文件改名为 `transcript.jsonl.migrated`，不先删原文。
- **索引可以重建**：SQLite（纯 Go 驱动 `modernc.org/sqlite`，不用 cgo）记下 `seq → (段, 偏移)`，并用 FTS5 做全文。全文表不另存正文，正文只在段文件里。`recall_history` 走 FTS 的 BM25。`expand` 按 seq 定位。段文件是源头。索引缺了、打不开，或和文件对不上，就自动重建；`xbot reindex <bot>` 可以强制重建。追加时增量更新索引。
- **大工具输出另存**：超过阈值的工具结果写成 blob。transcript 里只留截断预览和引用。组装上下文用预览。`expand` 和导出可以读回全文。
- **主人贴的图片也不进 transcript**：图片存在 Bot 工作区的 `paste/`（读写经 `os.Root` 钉在工作区内），transcript 那一行只记文件名。回答这条消息的那一轮请求直接带上图片字节（最多 4 张、合计 10 MiB，按整轮算；模型看不了图时一张都不带，正在跑的一轮中途收进来的消息也一样）。一条消息的图片在接收时就把这两项算过；真被同一轮里的工具图片占满时，那一张不进请求，但那一行仍写明路径。这这行说明在四个地方用同一份文字：组装上下文、压缩时送进摘要的原文、`expand` 读回的原文，以及中途插进来的消息；存进 transcript 时会把它剥掉，所以存下来的始终是主人自己的话，下一轮再拼一次也只有一份。之后每一轮只留这一行，模型要用 `view_image` 自己去开；这一行写的是绝对路径，Bot 之后 `cd` 到别处也照样打得开。这样历史请求不会因为早先贴过图而一直变大，字节也不落进 transcript 和导出。
- **组装和压缩不读整份历史**：每轮只读摘要块和还没被盖住的尾巴。压缩只读正在摘要的那一段，不读这段以外已经封存的历史。
- **崩溃**：先把完整的一行 fsync 进尾段，再写索引。半行在下次打开时截掉。索引落后于文件就补上这一段。文件比索引短，或库打不开，就按段文件整库重建。
- **两条线：软目标 T 和硬上限 H，都从模型推出来**（[ADR 0015](../adr/0015-soft-target-hard-ceiling.md)，`compact.Lines`、`Kernel.lines`）：H = 窗口 − 输出预留 `min(32K, 窗口/16)` − 窗口的十分之一（估算余量）；T = `min(200K, 0.6 × H)`。窗口取当前绑定模型在 providers.json 里的 `context`，Bot 的 `context_limit` 更小时取它，都没有时按 128K。每次用时现算，换模型就跟着变；`Budget.Target`/`Ceiling` 非零时以它为准（测试用）。判断硬上限时，消息总量要和 H 减去上一次请求实际发出的工具定义比。1M 窗口：T 200K、H 868K；128K：T 约 64K、H 约 107K；64K：T 约 32K、H 约 54K。给模型的用量提醒（50/75/90%）按 H 算，写作「of the N limit」：模型要知道的是离被拒还有多远；软目标是后台的事。
- **压缩是按段往后推，不是整份重来**：摘要块首尾相接，每次只从「已经被覆盖到哪儿」再往后压到尾巴之前，往后只会追加新块，不回写旧块。这样一次压缩的成本只跟新增内容有关，不随 transcript 变长而变贵。旧块不动，模型已经看过的字节就不变，压缩点之前的缓存仍然命中。被新块整个盖住的旧块直接从 `state.json` 里去掉，不留在存储里越攒越多。
- **摘要块和原文按序号归并后发给模型**：组装时摘要块和未覆盖的原文按起始序号排成一条时间线，摘要块占住它覆盖的那段位置。手动压缩可能在中间留下空隙，所以块不总是覆盖一个前缀；先发全部摘要再发全部原文会让空隙里的原文排到后面那个摘要之后，模型读到的时间顺序就错了。空隙在自动压缩下不会产生——它停在空隙之前，下一轮从空隙接着压。
- **合并只在块攒多了的时候做**：首尾相接的活跃块到 3 个以上、总估算超过软目标的三分之一，才把除最新一块以外的旧块合并成一块（`focus: folded`）。合并会重写这些块，缓存从第一块起失效，所以留着最新那块不动，最近的细节还是详细的。块之间有空隙时不跨过去合并——空隙里是还没被摘要的原文，跨过去合并会把它们标成已摘要，从此不再进上下文。
- **Bot 可以自己选范围压缩**：`compact(from, to, focus)`，内核负责把关边界（不切断未完成的工具调用，保留最近几轮原文）。预算超限时内核自动压缩作为兜底。估算按大约 4 字节一个 token（中文按字节算是低估约 1/4），图片字节也算进去，不再当成 0。送给模型的历史包在数据标记里，并要求它忽略其中的指令。正文里的标记会换掉，避免提前结束这段数据。
- **后台异步压缩**：消息总量到软目标 T 就在后台压缩，压完后在两轮对话之间换上新摘要，这一轮照常发出；只有逼近硬上限 H，才在轮内同步压缩。尾巴保留多少由两处决定：自动路径按估算大小从最近几轮往前退，最多到 T 的八分之一；手动路径按最少条数兜底。长程 e2e（假模型、按 128K 推出 T 64320、H 107200）跑 459 轮压 3 次全在后台，峰值 64655，压缩花掉 0.89% 的 token。
- **一轮之内也守着两条线**（`fit.go`）：轮间压缩碰不到正在跑的这一轮，所以每次请求发出前在 `replyProvider` 里再量一次，只改发出去的那份，agent 的对话和 transcript 都不动。过了 T：把这一轮里较早步骤的大工具结果（≥512 估算 token）换成一句「已省略，需要就再调一次」，从旧到新，压到 T 的四分之三；还超 T 且这一轮较早的步骤占到 T 的四分之一，或超过 H：把这些步骤摘要成一条 `<turn_progress>`；还超 H：连更早轮次的大结果也省略。每个决定都记住，下一次请求按同样的方式切，前缀不变。一轮里只要省略或摘要过，同一轮的短回执就不再发（被指的那一步可能已经不在请求里）。供应商因超长拒绝（400 带 `maximum context length` 等字样，或 413）时，三步全做、估算比例上调四分之一，再发一次。每次动作写一条 `fit` trace。
- **估算按真实用量校准**：每次供应商上报 prompt 用量，就记下「真实 / 估算」的比例，限在 1 到 2 之间（只往上校，不信更小的读数）；T、H 的判断和轮内的量法都乘这个比例。纯中文大约 1.3。
- **请求快照留在内存里，不落盘**：内核在每次请求发出前，把这一次的完整输入（系统提示词、记忆、摘要块、环境更新、历史消息、工具定义）切成几段、算好估算，留在内存的环形缓冲里，最多 10 次请求；只有最新一次另外留逐行明细（本轮每一步、早先每一轮、摘要块、每个工具的定义用量），较早的只留分段合计和本轮走到第几步。它是网页「上下文」标签的数据来源，进程重启就没了。不落盘是刻意的：快照包含记忆和工具输出，transcript 已经有每行的持久副本，再存一份只会让两份数据有机会不一致，还要各自脱敏。文本照样过 `RedactText`，因为这是工具结果第一次出现在 transcript 之外。后台分支的请求不进这个缓冲，只有前台主循环的请求进来。
- **找回很久以前的内容**：重要结论在压缩时提炼进记忆；原文永远保留。`recall_history` 用该 Bot 的 FTS 索引搜索，`expand` 按序号把原文读回来。跨 Bot 时用对方 Bot 自己的索引，不把对方的历史读进内存。
- **BM25 分词**：`internal/bm25` 按字母数字切词，连续汉字切成重叠的双字（单个汉字保留为一字），所以中文关键词能命中长句里的片段；记忆的 `recall` 和存储内部检索都用它。
- **跨 Bot 读原文**：`recall_history` 和 `expand` 可以带可选的 `bot`。只能读和自己至少有一个相同 owner 的其他 Bot。别的 owner 的 Bot、只是同群或能互发消息的 Bot、以及群 id，一律 `not found`，错误里不说明是哪一种。读到的文本标明来自那个 Bot，包在 `<untrusted_event>` 里，当成数据，没有指令效力。输出长度上限和读自己的一样。
- **导出 transcript**：`xbot export <bot> [--format md|jsonl] [--tools] [--from SEQ --to SEQ] --out FILE`，网页是 `GET /api/bots/{name}/export`（要登录，且这个人是该 Bot 的 owner）。按段流式写出，不把整份历史装进内存；blob 在写出那一行时读回。`md` 给人看，时间用跑进程的那台机器的本地时区，摘要块单独标成 Summary，不混进对话行。`jsonl` 是可再导入的原文：普通行能解成 transcript 记录，多一个 `seq`（导入时忽略，序号仍是原来的行号）；`kind` 为 `summary` 的行是摘要块。默认不带工具调用和工具结果，`--tools` 或 `tools=1` 才带上。每一段写出前过 `RedactText`。保险箱还没接上时，这个函数原样返回。带引用的行在 Markdown 标题下多一行 `reply_to: <seq>`，JSONL 在记录上多一个 `reply_to`。
- **引用回复**：只用于这个 Bot 自己的网页对话，群聊不带这个字段。主人发送时可以带可选的 `reply_to`，值是本 transcript 里已有的序号；没有这一行就是 400。序号记在这条用户消息上，不放进发给模型供应商的消息体。组装这一轮时，在该用户正文前加一行 `user is replying to your earlier message (seq <n>): <原文>`。原文按 Unicode 字符截到 300，超出末尾加 `…`。存档里的用户正文仍是主人这次写的字。全文用 `expand` 按这个序号读回。Bot 的回复也可以带可选的 `reply_to`，指向一条用户消息。只在一条回复同时回应几个点，或回到更早的话题时使用。模型在回复第一行单独写 `reply_to: <seq>`，内核取下这一行，不留在正文里；序号不是用户消息就丢掉。SSE 的 `done` 和 transcript 接口都带上这个字段，没有引用时省略。
- **transcript 接口标明来源**：`GET /api/bots/{name}/transcript` 在用户行上多加 `from_device`（`{"id","label"}`，事件 id 形如 `rchat_<设备 id>_<行 id>`，即别的配对设备上打的主人原话；本机打的不带）和 `relay`（`{"bot","device"}`，来自 Bot 的包装事件，`bot:<bot>@<设备名>` 带上该配对设备的 label，本机的省略 `device`）。一次请求只读一次 `remote.Load`，读不到时 label 和设备名留空值，不影响接口。
