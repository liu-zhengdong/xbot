# 插话时分叉

> **2026-10-20 起 `serve` 不再分叉**：主线拿全部工具，短活自己干，长活用 `dispatch` 交给预制子代理（[ADR 0028](../adr/0028-no-foreground-background-split.md)，取代 0016；见 [子代理](subagents.md)）。下面的分叉代码还在，`Kernel.AllowFork` 打开时只按「用户插话」分叉；2026-10-26 起没有前台工具次数或秒数上限，到点自动转后台（规则 3、4）已删除。旧 transcript 里的分支行照样读、导出、收成卡。
>
> **30 秒版（分叉打开时）**：Bot 正在干活时用户插话，这一轮立刻一分为二：后台照原样继续，前台在几秒内回答用户。可以同时有最多 3 个后台，只有碰同一资源的活才排队。

## 边界
负责：分叉、分支 transcript、前后台上下文、资源冲突排队、取消与崩溃。复用执行器任务（`bg_` id），不加新对象。不负责：普通子代理（见 [子代理](subagents.md)）。


## 怎么运转
**要做的事**：Bot 正在跑一轮时，用户插一句话，这一轮立刻一分为二。后台照原样继续，就像没收到这句话；前台另开一轮回答用户，任务状态变化经环境流进入前台。后台做完，结果作为事件投进收件箱。前台用已有的补充、排队、打断、取消工具管后台。

**分叉之前的做法**（`49733d0`）：一个进程拿着 `handle.lock` 跑一轮。网页发消息时拿不到锁，就把事件投进 `inbox.jsonl`；正在跑的那一轮在两步之间由 `absorbInbox` 把它接进当前对话。所以今天插话会被「吞」进正在干的活里，要等当前这一步（可能是一个很长的工具）跑完才看得到。transcript 是一份按段分开的只追加记录，进程内由 store 的互斥锁排序，seq 就是行号。子代理是 `exec` 里的任务，有自己的 `agents/<id>/transcript.jsonl` 和 `meta.json`，用 `KindSteer/Queue/Interrupt/Cancel` 控制。

## 不加新对象
被分出去的那一轮直接登记成一个执行器任务：`agents/<id>/meta.json`，`mode` 为 `fork-turn`，`id` 以 `bg_` 开头。补充、排队、打断、取消、查看进度都走现有的执行器控制接口，完成事件也走子代理的同一条路。区别只在于它的消息不写进 `agents/<id>/transcript.jsonl`，而是继续写主 transcript（理由见下）。

## 1. transcript：一份文件，每行带分支
- **只保留一份 transcript，不按分支拆文件。** 后台那一轮的前半段本来就在主 transcript 里，拆开会把一轮切成两个文件；`recall_history`、`expand`、导出、索引也都只认一份 seq。
- **`Entry` 加一个可选字段 `branch`**，值是后台任务 id，比如 `"bg_7"`。前台和平时一样不带，省略即主线。
- **分叉时先写一行标记**：`{kind:"fork", branch:"bg_7", from:<被分出那一轮的起始 seq>, task:"<一句话摘要>"}`。`from` 之后、标记之前的行属于后台（它们写的时候还不知道会被分出去），标记之后后台写的行都带 `branch`。只追加，不回头改旧行。
- **多个后台**：后台写的行一律带 `branch`，所以任何时候不带 `branch` 的写入者只有前台这一轮。再分叉时，`from` 之后、新标记之前不带 `branch` 的行就是被分出去的那一轮写的，几个后台的行互不混淆。
- **结束时再写一行**：`{kind:"fork_end", branch:"bg_7", status:"done|failed|cancelled|interrupted", steps:N}`。
- **seq 顺序**：两个分支在同一个进程里写，都经过 store 现有的互斥锁拿下一个 seq，所以 seq 就是真实的落盘先后，不会重号、不会倒退。每个分支内部的顺序（助手的工具调用在前、结果在后，结果按调用顺序写）由各自那一轮保证。跨分支只是按时间穿插，没有别的约定。
- **索引**：SQLite 多存一列 `branch`，可以重建，段文件里有就够。
- **界面**：transcript 接口每行带上 `branch`，标记行带上 `kind`。界面在 `fork` 标记的位置放一张**后台任务卡**：标题是任务摘要，副标题是「后台进行中 · 第 N 步」，带后台的进行中提示；属于这个分支的行（包括 `from` 到标记之间那几行）全部收进卡里，不进主消息流，点开看轨迹。`fork_end` 到达后卡片收成一行，状态只用图标，和确认卡一样。前台的消息照常往下排。
- **刷新**：按 seq 从头读，遇到 `fork` 就建卡，后面同 `branch` 的行往卡里放，遇到 `fork_end` 定状态。没有 `fork_end` 且后台还在跑（看 `meta.json` 的 `status`）就显示进行中。纯函数，前端和导出共用一套规则。

## 2. 各自的上下文
- **后台**：继续用它手里那份内存中的消息，什么都不加。分叉之后 `absorbInbox` 不再给它接用户的消息，用户的消息、以及之后新到的任何收件箱事件，都归前台。后台只收到前台通过控制接口发来的补充或排队。分叉时把当时的前台工作目录抄给这个分支；之后后台的 `cd` 只改自己的目录，前台的 `cd` 也不改后台。这份目录不写入 `bots/<name>/cwd`。前台仍用那份持久目录。后台冲突检测按调用方的目录解析相对路径。
- **前台**：按平时的规则组装，但跳过后台的行（`fork.from` 之后到标记之前的行，以及带 `branch` 的行）。被分出那一轮的那条用户消息留在前台，所以前台知道后台在干什么，也不会看到没配对的工具调用。任务状态从同一执行器和分支记录采样，有变化才在对话尾部追加环境流差异；不在用户消息前另插后台清单，不重复注入“后台任务正在执行”的指令。
- **后台结果怎么回来**：`fork_end` 时，内核往收件箱投一条完成事件（和子代理完成一样），内容是分支 id、状态、步数和结论指针。后台末条回复全文保存到已有任务目录的 `result.txt`，事件不再复制全文；回报至多附 256 字节的结果记录开头，整条记录不超过 256 字节时只给路径。副作用摘要保留；错误、预算停止原因与未读控制只给最多 512 字节的片段，完整详情同存结果文件。完成事件合计不超过 4096 字节。保存失败报告 failed。前台可用 `read_file` 分段读。前台下一轮读到它，决定怎么告诉用户。后台的中间过程永远不进前台的上下文，需要时用 `expand` 按 seq 读回。这样前缀缓存也保持确定。

## 3. 压缩与记忆抽取
- **有后台在跑时，压缩只碰 `fork.from` 之前的行**，相当于把 `protectSeq` 提到这个位置。
- 后台结束后，压缩照常覆盖这一段。摘要里后台那部分只用完成事件那一行代表，不逐条摘要分支的行。
- **记忆抽取同理跳过分支行**，只看完成事件，避免一件事被抽两次（后台中间过程一次、完成报告一次）。
- **记忆快照**：前台与派生子代理沿用固定的 Bot 记忆，不再按发送者切换。人物资料通过环境流有身份地追加；分支自己的成功记忆文件改动仍按原自写差异规则处理。
- 后台自己的上下文涨满时，按子代理到上限的方式收尾：`fork_end` 记 `failed`，原因写「上下文满」，不在后台里做压缩。

## 4. 导出与引用
- **导出**：按 seq 原样写出。`md` 里分支的行标题加 `[后台 bg_7]`，`fork` 和 `fork_end` 各写成一行说明。`jsonl` 原样带 `branch` 和标记行，导入时保留。
- **`reply_to`**：可以指向任何已有的 seq，包括后台的行，规则不变。用户引用后台卡里的某条，前台照常拿到那一行的引文前缀。Bot 回复的 `reply_to` 仍然只能指向用户消息。

## 5. 文件与资源冲突
- **有后台在跑时，前台的写操作自动排到相关后台之后**：写文件、shell 写操作、对外发送、删除这几类，内核用 `queue` 交给对应的后台，前台告诉用户已排队。模型不用自己选（[ADR 0002](../adr/0002-foreground-writes-auto-queue.md)）。
- 冲突按资源算：每个后台登记自己要碰的文件、仓库或工作目录；新的写操作或新后台和某个在跑的后台重叠，才排到它后面，不相干的并行。
- 这条规则放在那张权限表里判断（多一个条件：本 Bot 有活着的分叉），不在各工具里加检查，守门测试一起覆盖。
- **实现**（F3）：`review.ResourceOf(tool, args, workdir)` 给出一次调用写的资源：`write_file`/`edit_file`/`delete_file` 是 `file:<绝对路径>`，非只读的 `shell` 是 `dir:<cwd 或工作目录>`（`ShellIsReadOnly`：`ls`、`cat`、`git status/log/diff` 等，且没有重定向和管道），`code_start` 是 `repo:` 或 `dir:`。`reviewedTool.Run` 把它记在这一轮的 `resources` 里。前台的调用和某个在跑后台记过的资源相同，就不执行，作为一条 `conflict` 控制消息排进那个后台，工具结果告诉模型「已排到后台 bg_x 之后（队列 qN）」。后台之间不互相排队。
- **队列上限 5**：用户的 `queue` 和 `conflict` 合计最多 5 条，另外后台槽位满时等在收件箱里的用户消息也算（原因 `slot`）。满了以后：冲突的写操作回复「队列已满，没有建任务」，网页插话返回 429。每条排队项有原因（`queue`、`conflict` 带后台 id 和资源、`slot`）和位置，可以按 id 取消（`DELETE /api/bots/{name}/queue/{qid}`）。

## 6. 连续插话与响应时延
**目标**：任何时候用户发任何一句话，几秒内都有回复，连着插话也一样，而且不拖慢正在干的活。比较过的方案和被取代的「只有一个后台」见 [ADR 0001](../adr/0001-multiple-backgrounds.md)。

**规则：**
1. **插话即分叉**：正在跑的那一轮（满足门槛：跑满 3 秒或已调用过工具）分叉成后台，前台回答这句。不满足门槛就直接接进当前这一轮。
2. **多个后台**：已有后台时用户再要一件事，立刻开一个新的 `bg_` 执行器，已有后台不受影响。每个 Bot 最多 3 个后台同时跑（可配置），超出的排队。每个后台一张卡；环境流只追加这些任务状态的变化（id、摘要、步数）。
3. ~~前台的硬上限~~（已删，ADR 0028）：主线不限工具次数、秒数和工具种类。前台在跑时来的下一句，在两步之间接进前台这一轮（`absorbInbox`）。
4. ~~前台的活变长了就转后台~~（已删，ADR 0028）：长活靠规则让模型用 `dispatch` 交给子代理，内核不再到点硬转。旧 transcript 里的「已转到后台」行照常显示。
5. **后台只在自己的两步之间读控制消息**，从来不读用户的原话，所以插话再多也不打扰它，前缀缓存也不会被破坏。
6. 只有用户通过认证入口发来的消息会触发分叉。定时器、Webhook、其他 Bot 的消息照旧接进当前在跑的那一轮，有后台时就接进前台。
7. 第一版只做网页；终端仍把插话接进当前这一轮。

**时延保证**：前台要么空闲，要么在一个有上限的步骤里，所以用户的消息最多等一个前台步骤：一次模型调用加最多 10 秒的只读工具。后台的长工具不会挡住任何回复。验收按 p95 3 秒以内（假模型）来测。

**后台控制**（F3）：`steer`、`queue`、`interrupt`、`cancel` 发给 `bg_` id（网页 `POST /api/bots/{name}/agents/{bg}/steer|queue|interrupt|cancel`，模型用原来的子代理控制工具）。控制消息先是 `pending`，后台在当前工具调用返回之后、下一次模型调用之前读走，变成 `applied`，以带前缀的用户消息（`[用户的补充]`、`[排队]`、`[打断]`）写进它的分支。后台本来要结束时还有没读的控制，就带着它们再跑一轮。发给已结束后台的控制返回错误；后台出错或被取消时还没读的控制标成 `dropped`，写进完成事件。`cancel` 取消那一轮的 context，结束状态是 `cancelled`。`GET /api/bots/{name}/backgrounds` 返回在跑的后台、控制消息及状态、排队项（原因、位置、文件名）、最近 3 个结束的后台，供 F5 的「后台 N」角标和弹层用。

**后台的确认**（F3）：后台遇到要确认的操作，走 `Kernel.BackgroundApprove`。网页把它设成 `webApprove`，卡片写进 transcript（带后台的 branch），界面按 transcript 显示按钮，用户点了以后后台继续。没设的时候照旧拒绝。

**后台在跑时的其他事件**（F3）：后台拿着处理锁时 `serve` 的轮询拿不到锁，所以网页进程在等后台结束的循环里（`releaseWhenIdle`）拿 gate，把收件箱里的事件（定时器、其他渠道、别的后台的 `fork_end`）用 `proc.Drain` 处理掉。删除或改名 Bot 时 `forgetKernel` 取消它的后台、删掉锁记录并放锁。

## 7. 取消与崩溃
- **取消**：`cancel bg_7` 取消后台那一轮的 context，正在跑的工具按现有方式收尾；写 `fork_end{status:"cancelled"}`，并投完成事件。`interrupt` 和子代理一样，停在当前步，等新的指示。
- **前台的取消**（用户在界面点停止）只停前台，不碰后台。
- **按轮状态**：已挪进 `internal/kernel/turn.go` 的 `turn` 结构，`Kernel.turn` 指向当前一轮（F2 步骤 A）。
- **崩溃修复的占位结果**写在它所回答的那次调用所属的分支上。多个分支可以各有一条未答的调用：只要这条调用之后，它自己的分支里没有别的行（工具结果和标记除外），就能补；否则报错（`unresolvedCalls`）。
- **实现位置**（F2）：`internal/kernel/bgturn.go`。`Kernel.AllowFork` 打开后，`Handle` 把这一轮放在自己的 goroutine 里跑，每 300ms 和每步之间检查收件箱；有用户的新消息、这一轮已调用过工具或跑满 3 秒、后台不到上限时，写 `fork` 标记，这一轮之后写的行带 `branch`，`Handle` 立刻返回，调用方就能处理用户的新消息。这一轮从此不再接收件箱，不再往原请求流式输出；结束时写 `fork_end`、更新 `meta.json`，并以来源 `subagent`、类型 `fork_end` 投完成事件。工具代码通过 context 拿到自己那一轮的状态，不读 `k.turn`。分叉的判断和接收件箱互斥，已经接进这一轮的消息不会再触发分叉；最终回复写下之后不再分叉。
- **网页接入**（F2）：`web.Server.ForkTurns`（`serve` 打开）。进程内对同一个 Bot 的请求共享处理锁（`internal/web/holder.go`）：第一个请求拿锁，后来的请求把消息投进收件箱让正在跑的一轮分叉，拿到 gate 后作为前台回答；锁一直拿到没有请求、也没有活着的后台时才放。插话已被正在跑的一轮接进去时，按那一行所在的分支回复。分叉出去的请求以 `done{background: bg_…}` 结束。前台提示包在 `<background_tasks>` 里，界面不显示。网页发送不再被正在流式输出的回复挡住。后台遇到要确认的操作时先拒绝。
- **锁**：`handle.lock` 由同一个进程拿着，直到两个分支都结束。实现上要把 `Kernel` 上按轮的状态（`turnEvent`、`OnDelta`/`OnTool`/`OnResult`、`ReplySeq`、`Approve`）挪进一个 turn 结构，两轮各一份；网页的 `gate` 改成每个分支一个，不再整台 Kernel 一把。
- **谁来分叉**：拿着锁的那个进程。网页请求如果就在这个进程里，直接开前台的一轮，用 SSE 流式回给用户；如果锁在别的进程（比如终端），网页照旧把事件投进收件箱，持锁进程立刻（看 `inbox.Wait()`，不是等这一步跑完）分叉，前台的回复通过刷新 transcript 补到网页上。
- **崩溃恢复实现**：`Kernel.RecoverTasks` 在打开内核与首次 Handle 时走同一恢复入口。原 meta 的 pid 与进程启动身份能核实仍存活就继续观察；否则有 `fork` 无 `fork_end` 的分支补 `interrupted`、更新 meta 并投固定 EventID 的普通完成回报。未答工具调用仍由 `repairTail` 按原分支配对，重复打开不重做或重复报告。
- **崩溃恢复**：重启打开 transcript 时，找到有 `fork` 没有 `fork_end` 的分支，补写 `fork_end{status:"interrupted"}`，把 `meta.json` 标成 interrupted，并投一条完成事件：「后台 bg_7 因进程重启中断，做到第 N 步」。第一版不自动续跑，由前台下一轮决定要不要重做。半行照现有规则截掉。
- **后台只受墙钟预算约束，不按步数分段**（[ADR 0014](../adr/0014-no-background-segments.md)）。 后台从分叉那一刻开始计时，总时长不超过工作角色给的后台预算（`chat` 45 分钟、`dev` 2 小时，`profile set --background-max-time` 改，见 [多 Bot](multibot.md)）。预算每步之后由 `Guard` 检查，也在为一条排队控制消息另起一轮之前检查；用完时写 `<stop_reason>` 收尾，完成事件写明是预算停下的，没来得及读的控制标成未读。步数只剩一个防呆常量（`maxStepsGuard` 1000），不参与设计；以前那套「用满一段步数就自己再开一段、最多 4 段」的续段机制已删除，正是它把「上一段用完了步数上限」这种假用户消息写进了对话。
- **排队的控制消息另起一轮。** 后台本来要结束时还有没读的 steer / queue / interrupted，就带着它们再跑一轮；是不是再跑只看控制消息在不在，不看步数。

**网页界面**（F5）：`internal/web/static/app.js` 里以 `bg` 开头的函数。每 2 秒（页面可见时）以及每次发送结束后拉一次 `GET /backgrounds`；输入框里有正在写的追加指示时不重绘弹层；切换 Bot 后旧数据不再渲染。聊天里隐藏 `fork`/`fork_end` 标记行和 `fork_end` 事件，带 `branch` 的行上方加「后台」来源标。发给后台的控制消息和内核写给模型的注记（环境更新、提醒、完成门、停止说明、控制消息）一律靠 transcript 行的 `origin` 字段隐藏，界面不按文本开头猜；`skipMessage` 只读这个字段。字段是三态：`owner` 显示、`internal` 隐藏、空只出现在改动前的旧行（那些才回落到开头匹配）。

## 8. 验收与测试
**做完长什么样**：用假模型跑一个要 10 分钟的后台任务，中途用户连发 5 句话，每句都在 3 秒内（p95）看到回复，后台的总耗时和不插话时相比增加不超过 10%；同时跑 2 个互不相干的后台，期间再插话，两个都不受影响、各有一张卡，碰同一仓库的第三件活排在对应后台之后；界面上有后台任务卡在动；后台照常做完，完成后 Bot 主动告诉用户；刷新页面，卡片和前后台消息的顺序都还在。

**单元测试**（`go test ./...`）：
- store：两个 goroutine 并发追加，seq 连续、不重复，每个分支内部顺序不变。
- 组装：前台不含 `from` 之后的后台行，也没有没配对的工具调用；后台的消息里没有用户的新消息。
- 压缩：有活着的分叉时不越过 `fork.from`；结束后摘要和记忆抽取只用完成事件。
- 权限表：有分叉时前台的写类工具自动排到资源重叠的后台之后，只读的照常；守门测试覆盖新条件。
- 连续插话：第 2、3 句接进前台；长回合没人插话不会自己转后台（`TestLongTurnStaysOnMainLine`）；资源重叠的排到对应后台之后，不相干的并行；同时最多 3 个后台；非用户事件不分叉。
- 取消与崩溃：取消写 `cancelled`；伪造一份只有 `fork` 的 transcript，打开后补写 `interrupted` 并投事件。
- 导出与刷新：同一份 transcript 导出的 `md`、`jsonl`、界面分卡结果一致；`reply_to` 指向后台行可用。

**盒子回归**（`mockopenai` 脚本）：后台脚本是一个循环调用 `sleep 5` 的长任务；前台脚本回答一句话。用网页接口发起任务，5 秒后再发一句，检查：回复在 3 秒内到达，后台任务的 `meta.json` 在跑，transcript 里有 `fork` 和带 `branch` 的行，后台最后写出 `fork_end{done}` 并投完成事件，前台下一轮转告用户。再跑一遍取消的，以及在后台跑的时候 `kill -9` 进程、重启后看补写的 `interrupted`。网页截 2 倍截图：卡片进行中、收成一行、刷新后。
