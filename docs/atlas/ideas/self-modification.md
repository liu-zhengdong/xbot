# 自我修改要可控：过评测门、可回滚、留记录

> **状态**：候选，机制还没设计。本文写的是已经定下的三条规矩，以及现有的雏形；完整机制等 8 步计划和两周验收之后再设计。

> **30 秒版**：主人希望 XBot 将来能自己变好：从记忆，到提示词和技能，再到代码，一层比一层影响大。不管改哪一层，都守三条：改动要过评测门，证明没变差；改动要能撤回；每次改动都留下记录，说清改了什么、为什么。这三条在现在的 XBot 里已经有雏形，完整的自进化机制还没设计。

## 从一个场景说起
2026-10-17 主人提到最近很火的 RSI（递归自我改进）概念，想让 XBot 也能自进化，同时说这个机制自己还没怎么想好。当时把它记进了候选清单：分记忆、提示词和技能、代码三层，每层都经评测门、可回滚、留记录，等 7 个里程碑和两周验收之后再细化。

## 这个想法是什么
**越往下影响越大，门槛越高。** 改记忆只影响这个 Bot 怎么理解主人和事情；改提示词或技能影响它的所有行为；改代码影响所有 Bot。三层用同一套规矩，但越往下，评测要求越严、回滚越要可靠。

**过评测门。** 自己改出来的东西，和人改的一样要证明没变差。这和[评测把关](eval-gated.md)是同一条线：用普通套件改，用留出套件验收，四维成绩单任何一维不许退步。没有这条，自我改进很容易变成对着评测自我过拟合。

**可回滚。** 每一次修改都能撤回到上一个版本。代码和提示在 git 里，天然可回滚；记忆是只追加的日志，以最新为准，旧条目还在。

**留记录。** 改了什么、为什么、谁批准的，都追加进记录，不改写历史。transcript 只追加；每次确认决定写进 `decisions.jsonl`；仓库里的决策写成 ADR，只追加不删。

现在已有的雏形：Bot 改自己的人设和档案（`propose_persona`、`propose_profile`，以及直接写这两个文件）总要主人确认；`write_skill` 写盘前走确认卡；LESSONS.md 里同一条教训出现 3 天就升级成硬约束，这本身就是一条人参与的「从经验改规则」的路径。

## 它带来什么、代价是什么
好处是 Bot 能从长期使用里积累改进，而不是每次都靠人发现问题再改。代价和风险都不小：评测覆盖不到的地方可能悄悄变差，自动改动多了以后，人很难看懂系统为什么变成现在这样。所以在设计清楚之前，它只在候选清单里，不开工。

> 待确认：三层划分、「越往下门槛越高」和「已有雏形」这几段是 Bot 复刻整理的。哪一层允许 Bot 不经主人确认自己改、评测门由谁跑，主人还没定。

## 在仓库里体现在哪
