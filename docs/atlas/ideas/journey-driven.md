# 旅程驱动：先跑通一件事，再谈做完

> **30 秒版**：XBot 的进度单位不是功能、模块或里程碑，而是用户真的会做的一件事——一条旅程，从入口走到结果，有能观测的「怎样算对」。同一时间只推进一条，其余进候选清单按优先级排队。功能写完了、测试全绿，只算「已合入」；对着真入口端到端跑通才算「端到端通过」；用户日用了几天没问题，才算「用户日用通过」，这时它移进 `docs/guard/` 被一直守着，任何改动都不能让它退化。

## 从一个场景说起
2026-10-18 之前，XBot 的推进方式是列里程碑、按模块往上堆。每块都有测试、都是绿的，汇报说做完了，用户一用却到处是问题——六个基础体验（网页对话、记住事情、动手做事、忙时插话、主动唤醒、Bot 之间协作）功能都在，却没有一条能说「它一定是对的」。根子在两件事：「做完」由写代码的一方自己定、自己验；范围的增长速度超过了验证的速度。于是用户挑出这 6 条，先把它们补齐、跑到端到端通过，再开新的重点。

## 这个想法是什么
**进度的单位是旅程，不是功能。** 「保险箱」「网关」是实现，「让它用我的 token 调接口，token 不出现在对话里」才是旅程。一条旅程写清四件事：名字、入口、三到六步、怎样算对。「怎样算对」必须是能观测的结果——文件真的出现了、3 秒内有回复、重启后还记得；不写「体验良好」这种判不了对错的话。

**完成分三级，只有到第二级才能开下一个。** 已合入（测试全绿，代码进了主干）、端到端通过（对着真二进制、真界面把这条旅程跑通，已有旅程都没退化）、用户日用通过（用户实际用几天，这条旅程上没有新的阻塞问题）。只有「已合入」时不说「做完了」。

**一次只推一条，其余排队。** 候选清单按 P1–P4 排好，按顺序往下做；同一时间只有一条在做，它的设计在 `docs/dev/`，做完之前不开第二条。没排上的想法进候选清单，不当场开工；用户一次说了好几件事，只挑跟正在做的那条最相关的一件做，其余逐条记下并告诉他放了哪些。

**每条旅程配一条端到端冒烟用例。** 模型和第三方服务可以换成脚本化替身，但入口、装配、进程、界面都要用真的；在进程里自己拼一遍内部组件的测试不算端到端。用例按「怎样算对」写，由不写这次实现的一方来写，写实现的一方不能改用例的期望。每次合入前把已做好的旅程全部跑一遍。

**已做好的旅程不许退化，坏在最前面修。** 毕业后的旅程放在 `docs/guard/`，先于一切新功能；修完补一条回归用例。

## 它带来什么、代价是什么
好处是「做完了」有了用户能亲自核对的判据，范围也不再无限长：没排上的想法有地方去，不会一边堆功能一边漏验证。代价是慢——一条旅程要走到端到端通过才算数，比按模块堆功能慢得多；而且它要求有人写出真入口的冒烟用例，这件事不能省。另一个代价是取舍要用户做：先做哪条、某条旅程的「怎样算对」够不够，Agent 只能起草，不能自己定。

## 在仓库里体现在哪
`docs/dev/`（正在做的，有正在做的设计时才放，做完就删）；候选清单（不在仓库，在用户的 Obsidian，带 P1–P4）；[docs/guard/](../../guard/)（毕业后的旅程：长程运行、六条基本旅程）；[AGENTS.md](../../../AGENTS.md) 的「已有旅程与正在做的」；流程见技能 `liu-dev-workflow`，条目格式与 audit 见技能 `doc-atlas`。
