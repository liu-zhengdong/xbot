# 分级合并门槛与回归测试

> **30 秒版**：进 main 的改动要有证据：测试全绿才合并，每个修复带一条在旧代码上会失败的回归测试，没跑的检查写成「Not run」。把关的力度按改动大小分级：小改动测试绿了就合，大改动还要本地复测和一次独立评审。门槛的目的是让用户放心放手，而不是让每个改动都走一遍重流程。

## 从一个场景说起
2026-10-17 上午，三步内核改动接连合进 main，中间还夹着几个文档小修。每个小修都要等一轮复测和评审，用户看了觉得太重：如果只是简单修改，就不用复测完再审一遍了。于是当天定下分级门槛。同一天的 shell 后台化改动有两千多行，就走了重的那一档：独立评审找出两个严重问题（重启后的唤醒风暴、并发读写同一张表会让整个 serve 崩掉），打回去修完再合。

## 这个想法是什么
**测试是合并的唯一闸门。** AGENTS.md 写着：`go test` 全绿才合并，绿了就直接合进 main，不再等截图或确认；合入前跑三遍。测试和 CI 只用假模型，结果确定。

**修复必须证明自己修了东西。** 每个 bugfix 带一条回归测试，并且回退修复验证一次：这条测试在旧代码上会失败。没有这一步，测试可能只是在测一个本来就对的行为。LESSONS.md 的「做对了」里记着这样的例子（`2ed8ca3`、`7ff7738` 等，2026-10-16）。

**诚实标出没做的事。** 提交说明或 PR 里，把没跑的检查列成「Not run: …」，例如没跑真模型评测、没在浏览器里看过、没测公网可达。读的人据此判断还剩多少风险。

**按大小分级。** 用户 2026-10-17 定的规则：
- 小改动：文档、配置，或者几十行的单点修复。编码 Agent 的测试绿了、带了回归测试，就合。
- 大改动：几百行以上，或者碰内核主循环。在此之上再加本地复测和一次独立评审。

**教训会升级成规矩。** 踩过的坑记进 LESSONS.md；同一条在 3 个不同日子出现，就升级成 AGENTS.md 的硬约束。

## 它带来什么、代价是什么
好处是用户可以放心让 Bot 自己往前推：2026-10-17 用户说对推进比较放心，让它一直往前走，发现问题再来找。代价是大改动要多花一轮评审时间，而且「小」和「大」的边界要靠判断；拿不准时按大改动处理。门槛管不到的事，比如删除、对外发送、花钱、密钥，仍然先问用户。

## 在仓库里体现在哪
AGENTS.md 的「验证」「合并门槛」；[LESSONS.md](../../../LESSONS.md)；[MILESTONES](../../MILESTONES.md) 里每一步的「假模型回归」「未跑」记录。
