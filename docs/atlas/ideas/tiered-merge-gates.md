# 分级合并门槛与回归测试

> **30 秒版**：进 main 的改动要有证据：相关检查通过才合并，行为修复要有命中缺陷的回归证据，没跑的检查写成「Not run」。把关的力度按改动大小分级：小改动测试绿了就合，大改动补相关集成验证和独立评审，共用已有测试结果。门槛的目的是让用户放心放手，而不是让每个改动都走一遍重流程。

## 从一个场景说起
2026-10-17 上午，三步内核改动接连合进 main，中间还夹着几个文档小修。每个小修都要等一轮复测和评审，用户看了觉得太重：如果只是简单修改，就不用复测完再审一遍了。于是当天定下分级门槛。同一天的 shell 后台化改动有两千多行，就走了重的那一档：独立评审找出两个严重问题（重启后的唤醒风暴、并发读写同一张表会让整个 serve 崩掉），打回去修完再合。

## 这个想法是什么
**验证按风险选择，通过后停止。** 2026-11-01 用户取消固定三遍和每次全仓要求，现行执行规则统一见 [测试约定](../../TESTING.md)。默认只跑受影响检查一次；无法限定影响面或发版时才全仓一次。并发风险靠定向 race、同步与生命周期验证，不能用固定次数宣称并发安全。测试和 CI 继续只用假模型。

**修复要证明命中缺陷。** 优先复用已有行为用例，缺覆盖再补；复杂修复做定向旧代码红、新代码绿。不为文档、小样式或已经覆盖的行为重复新增测试，也不机械回退整包重跑。

**诚实标出没做的事。** 提交说明或 PR 里，把没跑的检查列成「Not run: …」，例如没跑真模型评测、没在浏览器里看过、没测公网可达。读的人据此判断还剩多少风险。

**按大小分级。** 设计和评审按大小分级；测试范围仍按当前影响面选择：
- 小改动：文档、配置，或者几十行的单点修复。相关检查通过就合；纯文档只检查内容、格式和链接。
- 大改动：几百行以上，或者碰内核主循环。补受影响的集成或真入口验证和一次独立评审；已有结果可复用，不让每一方再跑一套。

**教训会升级成规矩。** 踩过的坑记进 LESSONS.md；同一条在 3 个不同日子出现，就升级成 AGENTS.md 的硬约束。

## 它带来什么、代价是什么
好处是用户可以放心让 Bot 自己往前推：2026-10-17 用户说对推进比较放心，让它一直往前走，发现问题再来找。代价是大改动要多花一轮评审时间，而且「小」和「大」的边界要靠判断；范围不确定时先查依赖，不因拿不准就机械叠加全套检查。门槛管不到的事，比如删除、对外发送、花钱、密钥，仍然先问用户。

## 在仓库里体现在哪
AGENTS.md 的「验证」「合并门槛」；[LESSONS.md](../../../LESSONS.md)；[MILESTONES](../../MILESTONES.md) 里每一步的「假模型回归」「未跑」记录。
