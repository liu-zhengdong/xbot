# 内核要薄，约束放进 harness

> **30 秒版**：XBot 的内核只有几个抽象：Link、Event、收件箱、执行器任务。新能力先想办法用这几个抽象表达，不为特殊情况加新对象。内核薄，不等于什么都交给模型：凡是能由程序判断的约束，比如先读后改、步数上限、权限确认，都由内核和工具强制执行，不靠在提示里劝模型。

## 从一个场景说起
主人在网页上让 Bot 修一个 bug。Bot 跑到一半，主人又插了一句别的事。按「加功能」的思路，可以新造一个「后台会话」对象，配上自己的存储、控制接口和界面。XBot 没有这样做：被分出去的那一轮直接登记成一个执行器任务（`bg_` 开头），补充、排队、打断、取消都走子代理已有的控制接口，完成事件也走子代理的同一条路。区别只在于它继续写主 transcript。插话分叉是一个大功能，内核却没有多出一种新对象（[插话时分叉](../fork.md)）。

## 这个想法是什么
主人在「愿景与思想」里写过：内核要薄，机制最小够用；不为特殊情况加规则，新能力尽量用已有的抽象表达（2026-10-16 确认）。这句话有两层意思。

**第一层是对象要少。** 每多一种对象，就多一份存储格式、一套生命周期、一处可能出错的边界。XBot 选择让终端、网页、定时器、Webhook、MCP、浏览器、其他 Bot 都是 Link，让所有输入都变成同一种 Event 进同一个收件箱，让子代理和分叉后台共用执行器任务。确认规则也是这样收拢的：以前各工具自己决定要不要弹确认卡，规则散落各处，越改越宽；现在内核里一张权限表说了算，工具只负责写摘要（[ADR 0003](../../adr/0003-one-permission-table.md)）。

**第二层是约束要由程序执行，而不是写进提示。** 2026-10-17 用同一个 DeepSeek 模型对比 Claude Code 和 XBot，结论是 XBot 的优势在 harness，不在模型：Claude Code 没有步数预算和工作目录边界，模型就会一路查下去。同一份调研也发现，Claude Code 把「改之前先读」「写完不必重读」写在工具描述里，并由程序强制执行。XBot 随后的几步都按这个方向做：文件新鲜度由内核检查，没读过的文件改不了；打转由熔断计数，第二次直接停；该提醒的事走提醒通道，条件成立才出现，不常驻在系统提示里（[内核](../kernel.md)）。DeepSeek 对全局措辞很敏感，多一条常驻规则就可能拉低别的用例，条件触发的提醒副作用小得多。

**薄也意味着敢于不做。** 2026-10-17 对照 Claude Code 定计划时，文件检查点和回滚、hooks、规划模式被明确划掉：前两样用 git 就够，规划模式和 XBot 的设计不符（见 [候选清单](../../CANDIDATES.md) 的「不做」）。

## 它带来什么、代价是什么
好处是内核容易读懂、容易测，新功能落在已有路径上，现成的测试和恢复逻辑直接复用。代价是有时要多想一步，才能把一个新需求翻译成已有的抽象；而把约束做进程序，比在提示里加一句话费事得多，还要配测试。
