# 0019 永远放行，不弹工具权限卡

## 背景
XBot 是用户自己用的工具。[ADR 0003](0003-one-permission-table.md) 的权限表会为对外发送、删除、非 GET 的 HTTP、persona/profile 自改、未知和 MCP 工具弹确认卡；有了派活之后，子代理的这类调用也弹。每张卡都是用户没要的停顿，用户原话：「这个权限好烦……默认跟 Pi 一样吧，不设权限管控！反正是我自己用，我能控制」。

## 决定
1. **生产路径永远关掉工具权限卡**：`serve` 和 `chat` 打开的内核固定 `Permissive: true`，主 Agent 和子代理的调用都直接跑。`Permissive` 优先于旧实时开关，`permissions on` 不能重新打开工具许可卡。
2. **内核工具审查中的机器开关跟着关**：生产内核不因 `ask`/`off` 弹卡或拒绝工具调用。旧设置与权限表保留给直接构造的严格测试/评测内核。
3. **外部事件开的一轮也能改记忆**：webhook、别的 Bot 这类事件开的一轮碰记忆，不再弹卡。用户：「很多情况下外来事件比如 issue 增多、重大 BUG，凭啥不能修改记忆呢？这个围栏我觉得限制了很多情况下的可行性。」外部事件的内容仍包在 `<untrusted_event>` 里，从中抽出的记忆仍标「不可信」，只是写入不再被挡；提示里补一条 `EventMemoryRule`，让模型把和工作有关的事件记进记忆并写明来源（真实 DeepSeek 上没有这条时，它把 P0 issue 当成不可信数据、拒绝记）。
4. **只保留输入卡**：`links` 装连接器时用户在卡上填 key，这是输入框不是工具许可。触到保险箱、密钥、配置文件也不再硬弹确认卡；提问和其它非许可输入不在本次改动范围内。
5. **旧开关不再控制生产工具许可**：`xbot permissions on|off` 仍写 `permissions.json`，但不能覆盖生产内核的永远放行模式。
6. 权限表与严格模式保留供测试/评测：新工具照旧归类，守门测试照旧；直接构造的严格内核仍可验证原审查规则。

## 后果
- 删除、强推、对外发消息都不再先问；出了错靠用户自己发现、撤回。
- 测试里直接构造的内核默认仍按表确认，权限表的测试照旧有效。
- 外部事件能借提示注入改记忆、跑命令：用户接受这个代价。
- 2026-10-31 用户明确要求永远放行，取消旧版保险箱例外和生产实时开关；不改变密钥脱敏、保险箱加密与出站域名绑定。
