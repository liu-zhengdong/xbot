# 0010 跨设备靠开源信箱中继传 Bot 消息，不同步数据

## 背景
主人要在自己的 Windows 和 Mac 上各装一个 XBot（[ADR 0007](0007-local-first-desktop-app.md)），两台电脑通常都在 NAT 后面，笔记本还会合盖。主人定了：每台 XBot 只管自己的数据和自己对主人的理解，不做文件同步，不同电脑上的 Bot 通过 link 协议对话；网关要开源、能自建。旧的 [atlas/gateway.md](../atlas/gateway.md) 写的是"P2P 优先、中继兜底、Bot 地址带内网候选"，一直没实现。规格见 [GATEWAY.md](../GATEWAY.md)。

## 考虑过的方案
- **文件同步（FNS、Syncthing、现有 `nodesync`）**：主人否了。冲突合并、两份记忆打架，都是没必要的麻烦。
- **P2P 优先、中继兜底**：打洞要 STUN、候选交换、保活，两台机器还得同时在线。个人场景每天几十条消息，省下的延迟不值这份复杂度。
- **隧道式中继（像 Cloudflare Tunnel 那样把对方的 HTTP 端口转过来）**：收件设备必须在线；而且等于把整个 serve 接口暴露给另一端，攻击面太大。
- **信箱中继**：网关只存待取的信封，设备只出站连接；离线时代存，上线后取走即删。

## 决定
- 网关是存储转发的信箱中继，由 `xbot gateway serve` 提供，开源、单二进制、一个数据目录。
- 每个安装一对 Ed25519 密钥，公钥指纹就是安装 id。网关请求逐个签名；网关准入用一个加入口令（环境变量）。
- 配对只记在两台设备上；网关看得到哪两台安装在通信，看不到配对表。信封由发件安装签名，收件安装用配对时记下的公钥核对，并自己核对收件人、时间窗和见过的 id，防网关重放。
- 跨设备消息落地后就是现有的不可信 Bot 事件（`bot:<bot>@<设备>`），复用 `message_bot`、跳数上限和限流，内核不加新抽象。
- 载荷端到端加密作为单独一批（G4）跟上；在那之前只建议用自建网关。

## 后果
- 换来：设备不用开入站端口，不必同时在线；网关小到能自己审；网关被攻破也伪造不了消息，G4 之后也读不到内容（但没有前向保密）。
- 放弃：P2P 的低延迟；局域网内两台机器也要绕网关一圈。
- 代价：需要一台公网可达的机器跑网关（或放在 Cloudflare Tunnel 后面）。G4 之前网关能看到 Bot 名和消息原文。两台设备对主人的理解会慢慢有出入，靠 Bot 互相问来弥补，不靠同步。
- 现有 `nodesync` 的人的记忆同步和这个决定冲突，退役与否另定。（2026-10-18 已退役，见 [ADR 0012](0012-retire-node.md)）

## 什么时候重新考虑
- 同一局域网内的消息量大到延迟明显，或者网关成了单点、经常连不上：加 P2P 或内网直连。
- 要做跨用户通信：在这套身份上另加授权与联系人，不放宽同主人的假设。
