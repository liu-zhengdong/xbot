# 0031 商店在设置内收密钥，安装前真调通

## 背景
[ADR 0023](0023-connector-auth-followthrough.md) 第 2 条让密钥型商店条目走聊天确认卡，并写明密钥不进 API body。落地后商店点「添加」会关掉设置、替用户往聊天里发一句「请帮我安装…」，等 Bot 调 `links install` 再弹卡。用户（2026-10-27）明确这不是他定的路径：点添加/连接应在设置里弹层填密钥，真校验通过才算已添加。同日补充：所有商店连接器，包括无密钥的 Playwright，都要实际调通才标已装。

## 考虑过的方案
1. **保留聊天确认卡**：密钥不经设置接口，但要离开设置、代发消息，且依赖模型去调用工具。
2. **设置收密钥，只校验非空就写入**：路径对了，仍是 0023 要禁止的假成功。
3. **设置收密钥，探测成功才写入（选定）**。

## 决定
1. 商店的密钥型条目在设置内用 nestcard 弹层收密钥，`POST /api/apps` 接收 `secrets`（按目录顺序）。取代 0023 第 2 条中「走确认卡」「不进 API body」两处；其余照旧：密钥不进日志、transcript、`GET` 列表、聊天和模型提示，字段用人话标签。
2. 所有商店添加/连接在写配置或密钥之前做一次真实探测，失败不写任何东西：MCP 拉起并取得工具表；Playwright 还要真调用 `browser_navigate`；Context7 用密钥查一次上游；Telegram 调 `getMe`；飞书向 webhook 发一个不存在的 `msg_type`（飞书先验 token，错 token 回 19001，消息类型非法不会投递）；电脑操作截屏，浏览器起一个临时实例读页面。
3. 对话里 Bot 主动 `links install` 的确认卡路径不变。

## 后果
- 设置接口第一次接收密钥值；只在入口校验长度与条数，探测错误不回传原文（Telegram 的 token 在网址里）。
- 添加变慢：首次 npx 拉包可能要几十秒，接口上限 45 秒；同一时间只处理一个添加或移除。
- 飞书只验证了出站 webhook token；入站校验用同一个值，没法由我们主动探测。
- 已有配置的列表状态仍按配置与密钥存在判断，不重新探测。

## 何时重看
- 飞书改用应用凭据（app_id/app_secret）或别的连接器出现无法无副作用探测的凭据时。
- 商店改成按 Bot 安装、需要先选 Bot 时。
