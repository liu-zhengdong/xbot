# 0005 保险箱交给独立系统用户的守护进程

## 背景
M7 回归发现：保险箱密钥和密文都在 Bot 同一个系统用户能读的地方，Bot 的 shell 读出来就能解密。把密钥挪出 Bot 目录、读写要确认（第一步）只能防随手读取，同一用户的进程仍然读得到。

## 决定
- 保险箱抽象成后端接口（`vault.Backend`）：列名字、注入并转发请求、设置/删除。后面可以加 macOS Keychain 后端。
- Linux 后端：守护进程 `xbot vaultd` 以系统用户 `xbot-vault` 运行，独占密钥和密文（目录归它，0700）。Bot 进程通过 unix socket 连它；接入时用 `SO_PEERCRED` 核对对方 uid 在允许名单里，之后不再握手。
- 守护进程只做代理转发：Bot 发来带 `{{secret:名字}}` 的请求，它只在绑定域名上换成真值并转发，响应先脱敏再流回。永远不返回明文。
- 链路只走小控制消息和流式正文：一条长连接（HTTP/1.1 keep-alive），正文流式转发不整块缓冲；只有含占位符的请求体需要整体替换，上限 1 MiB；响应上限 8 MiB。目标：小请求额外开销 p95 < 5 毫秒，有基准测试。
- 同用户后端保留，作开发和测试的后备；配置了 socket 就用守护进程，没配就用后备。

## 考虑过的方案
- 守护进程发短期 token 给 Bot：token 本身就是凭据，泄露面一样。
- 每次请求重新鉴权：多一次往返，SO_PEERCRED 已经够。

## 后果
部署要多建一个系统用户和服务（命令见 atlas 安全节点）。同一用户的进程仍可以让守护进程向绑定域名发带密钥的请求，这由权限表的确认卡和域名绑定兜住。
