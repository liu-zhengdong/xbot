# 0016 前台只理解和派活，干活交给预制类型的子代理

## 背景
现在「随时能回话」靠插话分叉（[ADR 0001](0001-multiple-backgrounds.md)）：主人插话时，正在跑的一轮当场分成后台和前台。它做到了几秒内回话，但代价是：

- 前台和后台共用一份 transcript，靠 `branch`、`fork`/`fork_end` 标记区分；组装、压缩、记忆抽取、导出、界面都要认这套规则。
- 主线上下文装着干活的全部工具输出，长任务把它撑大，上下文管理的大部分难题出在这里。
- 只有网页会分叉，终端插话仍要等当前一步跑完。
- 模型面前有两种「放后台」：内核自动分叉、模型自己 `spawn`，限额各管各的。

## 决定
1. **前台只做理解、规划、派活、转告和整理记忆。** 它的工具在代码里限死：只读的快速工具（受现有前台上限约束）、记忆、派活和管子代理的工具。没有写文件、写类 shell、对外发送。想自己干也干不了，不靠提示词劝。
2. **干活的是预制类型的子代理。** 一个类型 = 工具白名单 + 提示片段 + 时间预算 + 交回格式 + 可选的模型。内置调研、开发、通用三种；主人可以在 Bot 目录里用文件加自己的类型。前台用一个派活工具选类型、写任务说明。
3. **子代理有自己的上下文和记录**，默认是空白上下文 + 任务说明 + 主人的记忆快照；主线 transcript 只记派出和结果。子代理不能再派子代理。
4. **插话分叉删掉。** 前台的每一轮本来就很短，主人的下一句最多等一个前台步骤；没有东西需要分叉。

## 考虑过的方案
- (a) 保留插话分叉，只加子代理类型：两套「放后台」并存，主线上下文仍被工具输出撑大。不采用。
- (b) 前台不留任何工具，什么都派：「今天几号」「看一下这个文件第 3 行」也要冷启动一个子代理，多花钱、多等几秒。不采用；前台留只读快速工具和上限。
- (c) 子代理默认带整段对话：起步上下文就很大，缓存也接不上主线。不采用；整段对话只在任务说明不够时按需 `expand`。
- ADR 0001 当年否掉的「由模型事先判断哪些活放后台」，理由是模型不一定听。本条不同：前台没有干活的工具，判断由工具集强制，不由模型自觉。

## 后果
- 取代 ADR 0001（多个后台靠分叉产生）和 ADR 0002（前台写操作自动排队：前台不再有写操作，排队只发生在开发类子代理之间）。ADR 0014 的时间预算改由子代理类型给出。
- 删除 `bgturn.go` 的分叉、transcript 的 `branch` 与 `fork`/`fork_end` 规则、前台写操作排队；旧 transcript 里已有的分支行仍要能读、能导出。
- 前台写任务说明的质量成为核心能力，要配提示词，并用真实 DeepSeek 评测。
- 界面的后台任务卡改成子代理卡，要先出原型。
