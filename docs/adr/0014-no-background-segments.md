# 0014 后台不做续段，也不再按步数限制

## 背景
2026-10-19 的 `389d091` 给后台加了「一段步数用完就自己再开一段」：最多 4 段，合计 4 倍步数上限，段与段之间写一条用户消息 `[继续] 上一段用完了步数上限，接着做，不要重复已完成的工作。`。

主人当天看到网页对话里出现了两句话，一句是上面的 `[继续] …`，一句是后台结束时模型的收尾，都不是主人说的。前一句尤其离谱：界面把它当成主人自己发的消息渲染成了气泡。

根因不在渲染。那条消息是内核真的写进 transcript 的一条用户角色记录，界面靠匹配文本前缀（`[主人的补充]`、`[排队]`、`[打断]`）来隐藏内部消息，`[继续]` 不在名单里，于是露出来了。同类问题还有 `<todo_gate>`、`<stop_reason>`：都是内核写给模型看的，都没有进名单。

而整套续段机制存在的理由，只是绕过「步数上限」这个本来就是拍出来的常量：chat 8 步、dev 24 步。8 步就是 8 次工具调用，做不了任何一次像样的调研或改代码；为了让后台不至于死在 8 步，才有了段、段上限、累计步数上限、段的墙钟上限、收益递减熔断这一整套。

## 决定
- **删除续段机制。** 后台一次跑到底：模型自己停下来、熔断硬停、或用完墙钟预算。删掉 `bgsegment.go`、对应测试、熔断里只服务续段的收益递减那一项、`[继续]` 这条消息。
- **步数降为防呆常量。** `maxStepsGuard = 1000`，只用来拦住永远不停下来的模型，不是设计变量，也不再是可配项（`profile set --max-steps` 删掉）。跟「按步数思考」一起删掉。
- **墙钟预算成为唯一的时长约束。** 后台从分叉开始算，chat 45 分钟、dev 2 小时；`profile set --background-max-time <分钟>` 可改，负数关闭（任何负值都归一为「关闭」）。预算在每步之后由 `Guard` 检查，也在「要不要为一条排队的控制消息再开一轮」之前检查：已经超时的后台不能因为收到一条控制消息就重新拿到全套工具。
- **内部写出来的行带来源。** transcript 的 `Entry` 加 `origin` 字段，三态：`owner`（主人真的说了、或给他看的卡）、`internal`（内核写给模型的注记）、空（只有改动前的旧行）。内核给自己写的每一行都标 `internal`；界面只读这个字段，删掉按文本前缀猜的过滤。空值只服务旧数据——前缀匹配那份清单不会再被新注记用到，主人的消息也不受它影响（他打一句以 `[继续]` 开头的正常话不会被藏起来）。

## 考虑过的方案
- **(a) 只把 `[继续]` 加进界面的过滤名单**：能盖住这次的现象，但下次内核再写一种注记，就会再暴露一次。每次都要改前端，且改错了没人拦。不采用。
- **(b) 保留续段，只把步数调大**：续段机制的每一段都要多付一次「停下并总结」的模型调用，那条假消息也还在，只是更少见到。补丁留着。不采用。
- **(c) 删续段、步数降为防呆、预算可配、内部行带来源**：四件事一起做，主人选这个。

## 后果
- 后台能连续工作到预算用完，而不是每 8 或 24 步被打断重来一次。
- 每次续段省下一次「停下并总结」的模型调用。
- 界面不再可能把内核的注记显示成主人的话；以后新增注记只需在写入处标 `internal`。
- 旧的 `[继续]` 行仍留在已有 transcript 里，靠开头清单继续隐藏。
- 熔断少了收益递减一项，剩五项：重复输出、同工具同参数、文件来回改、同一失败反复轮询、连续 3 次确认被拒。
