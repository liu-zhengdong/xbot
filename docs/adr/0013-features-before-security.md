# 0013 现阶段先把功能调通调顺，安全只留接口

## 背景
XBot 现在还没有用户，只有主人自己在用。确认卡、shell 黑名单、保险箱路径确认、不可信回合碰记忆时出卡、文件新鲜度拒写，这几道关一层层加上来，主人实际用下来的感受是：Agent 总被拦，活干不下去。主人自己绑的 Telegram、飞书发来的消息，也被当成不可信内容处理（`link.OwnerTrusted` 只认终端、网页和跨设备主人）。2026-10-18 的整体 review 指出，按来源把关等安全缺口还很大；主人当天决定：这些先不做。

## 考虑过的方案
- **先补安全，再调功能**：要等安全做完，才知道功能好不好用。产品还没人用，这个顺序不对。
- **把现有的关全删掉**：以后接安全时要从头来，权限表的归类也会丢。
- **留接口、不加新的安全工作，挡活的关默认放行**：主人选这个。

## 决定
- 现阶段最重要的是把功能调通、调顺。安全只留接口，不再加新的安全工作：按来源和污染状态把关、对抗评测、8 步内核计划里的 M8 权限规则都暂缓。
- 保留的接口：`review.Table` 一张权限表，以及「新工具必须在表里归类」的守门测试（AGENTS.md 硬约束不变）；内核的统一审查入口 `reviewCall`；保险箱的 `{{secret:名字}}` 占位和出站注入；`decisions.jsonl` 留痕。
- 计划中、还没落地的改动：确认卡、shell 黑名单、保险箱和配置路径出卡、不可信回合碰记忆时出卡、文件新鲜度拒写，统一收进一个开关，默认放行，代码先不删；主人绑定的 Telegram、飞书发来的消息按主人消息处理。落地后在 [security.md](../atlas/security.md) 写清现行行为，并刷新 `verified`。
- 本 ADR 不取代 [ADR 0003](0003-one-permission-table.md)：确认仍然只由那张表决定，只是现阶段大多数分类默认不出卡。

## 放弃了什么
- 暂时没有对提示注入的防护：不可信内容能驱动 shell，`curl` GET、`git push`、`ssh` 都能把数据带出去，确认卡也不再兜底。
- 任何知道 Telegram Bot 用户名的人都能给它发消息，代码不按发送者过滤。

## 后果
- review 发现的安全缺口留在这里备查，不排进当前的里程碑。
- 新加的功能仍然要在权限表里归类，所以以后接安全时，不用回头一个个补分类。

## 什么时候重新考虑
- 有了主人以外的用户，或者打算对外发布、开源安装包。
- 连接器要接主人以外的人（跨人通信、群聊）。
- 出现一次真实的误操作或数据外泄。
